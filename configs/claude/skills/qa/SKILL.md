# 계획자 QA — 질문과 리뷰를 받으며 작업 실행

계획을 세운 Claude 세션(이하 "계획자")을 참조하며 작업을 실행하는 skill 이에요. 계획자는 계획 당시의 컨텍스트를 전부 갖고 있으니, 작업자(나)는 두 가지를 계획자에게 맡겨요:

1. **질답** — 계획의 판단 근거가 궁금하거나 실행에 문맥이해가 필요할 때 물어봐요.
2. **리뷰** — 작업 결과가 계획과 일치하는지 확인받고, 틀어진 부분을 바로잡아요.

## 입력

`/qa {session-id}, {작업 지시}` 형태예요.

- `{session-id}` — 계획을 세운 Claude 세션의 ID (UUID). 예: `716f1865-e27a-47b1-bff1-43b866104cab`
- `{작업 지시}` — 무엇을 할지. 계획 아티팩트 URL, 계획 문서 경로, "첫번째 작업을 시작" 같은 문장이 섞여 올 수 있어요.

예시:

```
/qa 716f1865-e27a-47b1-bff1-43b866104cab, https://claude.ai/code/artifact/c677bbaf-... 의 첫번째 작업을 시작.
```

## 계획자 호출 방법 — client-server 모델

계획자 호출은 **요청 1회 = 응답 1회**로 끝나는 client-server 모델이에요. 세션은 요청 없이는 스스로 아무것도 하지 않아요. 그래서 응답이 "~하겠습니다 / 진행할게요 / 리뷰해보겠습니다"처럼 **실행 의사만 밝히고 결과가 없으면, 그 일은 아직 일어나지 않은 것**이에요. 알아서 해주겠거니 기다리지 말고, 반드시 그 응답을 낸 세션의 session_id 로 액션 요청을 다시 보내 실제로 실행시켜요.

**공통 커맨드:**

```bash
claude --resume {resume 대상 session-id} [--fork-session] -p "{프롬프트}" --output-format json | jq -r '"\(.[0].session_id)\n\(.[-1].result)"'
```

- 출력 첫 줄 = **이번 응답을 낸 세션의 session_id** (후속 액션 요청의 resume 대상), 둘째 줄 = 응답 본문(result). session_id 는 매번 기록해둬요.
- `--output-format json` 을 빼면 text 로 나와서 jq 가 실패해요.

**요청 방식은 3종이에요. resume 대상이 달라요:**

| 요청 | resume 대상 | `--fork-session` | 용도 |
|---|---|---|---|
| **질문** | 계획자 session-id | 붙임 | 판단 근거·문맥 질문. 매번 계획자에서 새로 포크 |
| **리뷰** | 계획자 session-id | 붙임 | 작업 결과 리뷰 요청. 응답의 session_id 를 "리뷰 세션"으로 기록 |
| **액션** | 직전 응답의 session_id | 안 붙임 | 이전 응답에 대한 후속 실행 요청 — "하겠습니다" 이행 지시, 재리뷰, 지적에 대한 추가 문의 |

**액션 규칙:**

- 어떤 응답이든(질문/리뷰 불문) 실행 의사만 밝히고 결과가 없으면, 그 응답의 session_id 로 액션 요청을 보내요: `"방금 하겠다고 한 것을 지금 그대로 진행하고, 결과를 응답에 담아줘."` 결과가 올 때까지 이어가되, 2회를 보내도 의사표명만 반복되면 멈추고 사용자에게 보고해요.
- 액션 응답에도 새 session_id 가 와요. 매번 다시 기록하고, 다음 액션은 항상 **가장 최근 응답의 session_id** 로 보내요.
- 액션에는 `--fork-session` 을 붙이지 않아요 — 직전 대화의 맥락이 이어져야 하니까요.

**호출 시 반드시 지킬 것:**

- **질문 포크는 매번 새로 만들어지고 기억이 이어지지 않아요.** 이전 질답 내용을 계획자가 기억한다고 가정하지 말고, 프롬프트마다 필요한 배경을 자기완결적으로 담아요. 반대로 리뷰 세션은 session_id 로 이어가므로 맥락이 유지돼요.
- **아래 템플릿의 지침 블록을 매번 프롬프트에 포함해요.** 지침 없이 질문만 보내면 계획자가 컨텍스트 밖의 추측으로 답할 수 있어요.
- 응답에 수 분이 걸릴 수 있으니 Bash `timeout` 을 600000 으로 줘요.
- 프롬프트가 여러 줄이면 따옴표 이스케이프 대신 임시 파일(scratchpad)에 쓰고 `-p "$(cat {파일})"` 로 보내요.
- 호출이 실패(세션 미존재, 인증 문제 등)하면 멈추고 사용자에게 보고해요 — 계획자 없이 추측으로 진행하지 않아요.

## 진행 절차

### 1. 계획 파악

- 작업 지시에 아티팩트 URL 이 있으면 WebFetch 로 읽어요. 파일 경로면 Read 로 읽어요.
- 계획 문서만으로 "무엇이 첫번째 작업인지 / 완수조건이 무엇인지"가 불분명하면, 시작 전에 계획자에게 첫 질문으로 물어요 (2단계 질문 템플릿 사용).
- 작업 대상 디렉터리를 확정해요. 리뷰 단계에서 절대경로로 넘겨야 하니 시작할 때 기록해둬요.

### 2. 작업 실행 + 질답

계획대로 작업을 수행해요. 작업 중 다음 상황이면 혼자 추측하지 말고 계획자에게 물어요:

- 계획의 판단 근거가 궁금할 때 ("왜 A 방식으로 정했는지")
- 계획에 없는 상황을 만났을 때 (계획이 가정한 전제와 실제 코드가 다를 때)
- 계획의 문장이 두 가지 이상으로 해석될 때

**질문 프롬프트 템플릿:**

```
너는 이 세션에서 계획을 세운 계획자다. 아래 질문에 답하되, 다음 지침을 지켜라:
- 이 세션의 컨텍스트(계획 당시 읽고 판단한 내용)에 있는 근거로만 답한다.
- 계획 당시 고려하지 않았던 사항이면 "고려하지 않았다"고 명시한다. 지금 새로 지어내서 답하지 않는다.
- 놓친 부분이면 "놓쳤다"고 인정한다.
- 근거가 있으면 계획의 어느 부분인지 함께 말한다.

[질문 배경]
{작업 중 어떤 상황에서 나온 질문인지 1~3줄. 관련 파일 경로 포함}

[질문]
{질문}
```

답변 처리:

- 계획자가 근거를 대며 답하면 → 그 판단대로 진행해요.
- 계획자가 "고려하지 않았다 / 놓쳤다"고 답하면 → 계획에 없는 갈림길이 생긴 거예요. 방향이 자명하면 진행하고 근거를 한 줄 남기고, 되돌리기 어렵거나 계획의 다른 부분에 영향을 주면 AskUserQuestion 으로 사용자에게 물어요.
- 어느 쪽이든 **계획과 다르게 진행하기로 확정되면 계획이 변경된 거예요** → 진행하기 전에 [계획 변경 시 — ADR 기록](#계획-변경-시--adr-기록)을 수행해요. 이때 액션 요청은 그 변경을 논의한 질문 포크의 session_id 로 보내요.

### 3. 리뷰 요청

작업이 완수조건에 도달하면 계획자에게 리뷰를 받아요. 최초 리뷰는 계획자 session-id 에서 포크하고, **응답의 session_id 를 "리뷰 세션"으로 기록**해요 — 이후 재리뷰·후속 문의는 전부 이 리뷰 세션에 액션 요청으로 보내요.

리뷰 응답이 "리뷰하겠습니다 / 살펴보겠습니다"처럼 의사표명으로 끝나면, 리뷰가 온 게 아니에요. 액션 규칙대로 그 session_id 에 실행 요청을 보내 실제 리뷰 결과를 받아요.

**리뷰 프롬프트 템플릿:**

```
{작업 디렉터리 절대경로}: 이 워크디렉터리를 리뷰해줘. 다음 지침을 지켜라:
- 네가 세운 계획과 구현이 일치하는지를 본다. 판단 기준은 동작과 구조다.
- 계획에서 틀어진 부분만 지적한다. 계획 범위 밖의 개선 제안은 하지 않는다.
- 컨벤션·스타일·네이밍·포맷 문제는 지적하지 않는다.
- 사소한 문제는 가져오지 않는다. 계획 기준으로 결과가 달라지는 것만 가져온다.
- 지적마다 근거를 붙인다: 계획의 어느 부분과 어긋나는지 + 코드의 어느 파일인지.
- 지적할 것이 없으면 "계획과 일치"라고만 답한다.

[이번에 수행한 작업]
{작업 범위 요약 1~5줄. 이번 작업이 계획 전체가 아니라 일부(예: 첫번째 작업)라면 그 범위를 명시}
```

### 4. 리뷰 반영

- 지적이 "계획과 어긋난 구현"이면 → 수정하고, **리뷰 세션의 session_id 로 액션 요청**을 보내 재리뷰를 1회 받아요 (새 포크가 아니에요 — 직전 지적의 맥락이 이어져야 해요). 재리뷰 요청에는 무엇을 어떻게 고쳤는지 요약을 담아요. 재리뷰에서도 지적이 반복되면 멈추고 사용자에게 상황을 보고해요 (무한 루프 방지).
- 지적이 "계획 자체의 결함"으로 보이면 → 내가 계획을 고치지 않아요. 사용자에게 AskUserQuestion 으로 알려요 (계획 수정은 계획자와 사용자의 몫이에요). 사용자 결정으로 계획이 바뀌면 [계획 변경 시 — ADR 기록](#계획-변경-시--adr-기록)을 수행해요. 이때 액션 요청은 리뷰 세션의 session_id 로 보내요.
- "계획과 일치" 응답이면 → 완료.

### 계획 변경 시 — ADR 기록

질답이든 리뷰든, **계획과 다르게 진행하기로 확정된 순간마다** 계획자에게 변경점을 계획 아티팩트 최하단에 ADR 로 기록시켜요. 기록 없이 계획과 다르게 진행하면, 다음 작업자(또는 다음 리뷰)가 옛 계획을 기준으로 판단하게 돼요.

보내는 곳: 그 변경을 논의한 세션의 session_id (질문 포크 또는 리뷰 세션) 에 **액션 요청**으로 보내요. 그 세션이 계획 컨텍스트와 변경 논의 맥락을 둘 다 갖고 있어요.

**ADR 기록 프롬프트 템플릿:**

```
계획이 변경되었다. 계획 아티팩트({아티팩트 URL})의 최하단에 아래 변경점을 ADR 로 추가해줘. 다음 지침을 지켜라:
- 아티팩트 최하단에 "## 계획 변경 기록 (ADR)" 절이 없으면 만들고, 있으면 그 아래에 이어서 추가한다.
- ADR 번호는 기존 마지막 번호 +1 (첫 기록이면 ADR-1).
- 계획 본문의 다른 부분은 고치지 않는다. 변경 이력은 ADR 로만 쌓는다.
- 아티팩트에 실제로 추가를 완료한 뒤, 추가한 ADR 전문을 응답에 담아라. "추가하겠다"는 예고로 끝내지 않는다.

[ADR 내용]
### ADR-{번호}: {변경 한 줄 요약}
- 날짜: {YYYY-MM-DD}
- 맥락: {왜 변경이 필요했는지 — 어떤 질문/리뷰/발견에서 비롯됐는지}
- 결정: {계획의 어느 부분을 무엇에서 무엇으로 바꾸는지. 검토 후 버린 대안이 있으면 함께}
- 영향: {다른 작업 항목·완수조건에 미치는 영향. 없으면 "없음"}
```

기록 확인:

- 응답에 추가된 ADR 전문이 없으면 액션 규칙대로 재요청해요.
- 응답을 받은 뒤 WebFetch 로 아티팩트를 다시 읽어 최하단에 ADR 이 실제로 붙었는지 확인해요. 안 붙어 있으면 client-server 원리대로 아직 안 된 거예요 — 다시 액션 요청을 보내요.
- 계획이 아티팩트가 아니라 파일이면, 같은 템플릿으로 파일 경로를 주고 파일 최하단에 추가시켜요. 확인은 Read 로 해요.

### 5. 보고

작업 완료 후 사용자에게 보고해요:

1. 수행한 작업 요약 (계획의 어느 부분인지)
2. 질답 내역 — 질문/답변 요지 한 줄씩. 계획자가 "고려 안 함/놓침"을 인정한 항목은 반드시 표시
3. 리뷰 결과 — 지적 사항과 반영 여부
4. 계획과 다르게 진행한 부분이 있으면 그 근거와, 아티팩트에 기록된 ADR 번호

## 주의

- 이 skill 의 핵심은 **작업자가 혼자 판단하지 않는 것**이에요. 계획의 근거가 궁금한데 묻지 않고 추측으로 진행하는 것이 가장 흔한 실패예요.
- **"~하겠습니다"를 완료로 착각하는 것**도 흔한 실패예요. client-server 모델이라 세션은 요청 없이 아무것도 실행하지 않아요. 실행 의사만 온 응답에는 반드시 그 session_id 로 액션 요청을 보내 결과를 받아요.
- 반대로 계획 문서에 이미 명시된 것을 다시 묻는 것도 실패예요. 묻기 전에 계획 문서에서 먼저 찾아요.
- **ADR 없이 계획과 다르게 진행하는 것**도 실패예요. 계획 변경이 확정되면 진행 전에 ADR 기록부터 시켜요. 사소해 보여도 계획 문서와 실제 진행이 달라지는 순간이면 기록 대상이에요.
- 리뷰 지적 중 동작·구조와 무관한 것(스타일, 취향)이 섞여 오면 반영하지 않고, 보고에 "리뷰 지침 밖 지적이라 제외"로 남겨요.
- git 리포지토리에서 작업한다면 전역 형상관리 규칙(브랜치·워크트리·커밋·PR)을 그대로 따라요.
