# sdd-draft — 구현 전 기획 초안

설명 한 덩어리를 받아, 마스터가 결정만 내리면 구현에 들어갈 수 있는 기획 초안을 쓴다. 코드는 바꾸지 않는다.

`spec-build` 와 다르다. `spec-build` 는 이미 있는 PR·브랜치를 검토하는 문서이고, 이 스킬은 아직 코드가 없는 기능의 요구사항을 처음 세우는 문서다.

## 형식 고르기

`{description}` 을 보고 하나를 고른다.

- "artifact", "아티팩트", "공유 문서", "Docs 로" 가 있다 → 「공유 문서 경로」
- 없다 → **기본값 「마크다운 경로」**

형식을 가리키는 말은 떼고, 나머지를 설명으로 쓴다.

## 설명 읽기

설명에서 아래를 뽑는다. 없는 것은 비워 두고 초안에서 채운다.

- 구현하려는 것: 기능 이름 하나 (예: 제휴카페). 문서 제목은 `{기능} 기획 초안`
- 도메인 언어: 마스터가 정의한 용어. 정의 문장을 그대로 옮기고 @결정 을 붙인다
- 목적과 정해진 원칙: 마스터 문장 하나에 @결정 하나
- 템플릿: 마스터가 요구사항 템플릿을 주면 그 템플릿이 이 문서의 「요구사항 템플릿」보다 우선한다
- 저장 경로: 경로처럼 보이는 문자열(`docs/…`, `*.md`)

설명이 비어 있으면(무엇을 만들지 없음) 쓰지 말고 무엇의 기획 초안인지 한 번 묻는다.

## 마크다운 경로

### 저장 경로 정하기

경로가 정해지기 전에는 파일을 쓰지 않는다.

- 설명에 경로가 있다 → 그 경로
- 없으면 현재 리포의 `origin/main` 에서 기획·스펙 문서 자리를 찾는다: `git ls-tree -r --name-only origin/main | grep -i -E '(^|/)(specs?|plans?|rfcs?|prd|기획)/' | head`
    - 후보 디렉터리가 정확히 하나이고 그 안에 비슷한 기획 문서가 있다 → 그 디렉터리. 쓰기 전에 채팅에 "{경로}에 씁니다" 한 줄을 남긴다
    - 후보가 없거나 둘 이상이다 → **모호하다.** `AskUserQuestion` 한 번으로 묻는다. 찾은 후보와 기본안 `.claude/specs/{YYYY-MM-DD}-{slug}.md` 를 옵션으로 주고, 추천안을 첫 옵션에 둔다
- `slug` 는 영어 kebab-case 50자 이내 (예: `2026-11-02-partner-cafe.md`)
- 같은 파일이 이미 있으면 덮어쓰기 전에 읽고, 갱신인지 새 파일인지 한 번 묻는다
- 마스터가 요청하기 전에는 이 파일을 커밋하지 않는다

### 쓰는 순서

- **뼈대 먼저.** Write 로 제목, 기준 날짜, 「절 구성」의 `## 절` 헤딩, 절마다 `(작성 중)` 한 줄을 만든다
- 「조사」를 한다
- Edit 로 절 하나씩 채운다. 절 하나를 채울 때마다 채팅에 "지금 {절} 작성 중" 한 줄을 남긴다
- 결론 절은 마지막에 쓴다. 결정 목록이 다 나와야 쓸 수 있다
- 다 쓰면 `(작성 중)` 이 남았는지 검색해 없앤다

### 마크다운 형식

- 표는 요구사항의 「업무 규칙」과 「도메인 언어」에만 쓴다. 마스터 템플릿이 표를 쓰기 때문이다. 나머지는 2단 불릿
- 인수 조건은 템플릿대로 숫자 목록을 쓴다. 나머지 순서는 "단계 1 —" 같은 라벨로 준다
- 흐름 그림은 ```mermaid `flowchart LR` 블록. 노드 라벨에 예시 숫자를 넣고, 그림 아래에 읽는 법 한두 문장

## 공유 문서 경로

`spec-build-artifact` 의 「도구 확인」「Docs 경로」「대체 경로」를 그대로 따른다. 다른 점만 적는다.

- 뼈대의 `pending` 블록은 「절 구성」의 절마다 하나다. `intent` 에 절 이름과 들어갈 내용을 적는다
- 흐름 그림은 widget 다이어그램으로 그리고 screenshot 으로 확인한다
- 표는 어디든 써도 된다. 문서 화면이 표를 그려 주기 때문이다
- 다 채우면 문서 링크와 남은 결정을 프로젝트 메모리에 `reference` 로 남긴다. 다음 세션이 같은 문서를 찾게 하기 위해서다

## 조사

초안의 목적은 결정을 끌어내는 것이다. 조사는 결정과 요구사항에 필요한 만큼만 한다.

- `git fetch` 후 `origin/main` 기준으로 읽는다 (`git grep … origin/main`, `git show origin/main:{path}`)
- 설명의 용어·개념과 닮은 기존 기능을 찾는다: 테이블·마이그레이션, 서비스, 정산·결제 주기, wiki 스펙
- 찾은 것은 「기존 시스템과 맞닿는 곳」에 `@사실 ({경로})` 로 적고, 요구사항과 결정의 근거로 쓴다
- 확인하지 못한 것은 "확인하지 않았다" 로 적는다. 짐작을 @사실 로 쓰지 않는다
- 마스터 문장끼리 부딪히는 곳을 찾는다. 같은 용어가 문장마다 다른 뜻이면 결정 항목으로 올린다

## 절 구성 (이 순서)

해당 없는 절은 지우지 말고 "해당 없음 — {이유 한 줄}" 로 남긴다.

### 결론 / 필요한 결정

- 2~4줄 결론: 이 기능이 무엇이고, 지금 초안이 어떤 해석 위에 서 있는지
- 먼저 정할 결정 ID 목록 (최대 5개). 다른 결정이 이 답에 따라 달라지는 것부터
- 남은 결정 개수

### 도메인 언어

- 표: 용어, 뜻, 표기. 마스터 정의는 고치지 않고 @결정
- LLM 이 새로 붙인 이름은 @초안 으로 따로 적는다
- 용어끼리 부딪히는 곳: 어느 문장과 어느 문장이 다른지 인용하고 → 결정 ID

### {기능}이란

- 목적 한 문장
- 참여자: 누가, 무엇을 하는지, 돈·데이터가 어떻게 오가는지
- 정해진 원칙: 마스터 문장을 불릿 하나씩, 모두 @결정
- 비슷한 기존 기능이 있으면 차이를 적는다

### 핵심 흐름

- 구체 예시 1건으로 처음부터 끝까지 보인다 (예: 정가 5,900원 아메리카노 1잔 주문 → 누가 언제 얼마를 받는지)
- 금액·날짜·수치는 실제 숫자로 쓴다. "일정 금액" 같은 말을 쓰지 않는다
- 그림 제목은 주제가 아니라 결론 문장이다

### 요구사항

- 첫 문장: 요구사항 개수와 각각 어디서 나왔는지 (마스터 문장, 외부 요청 등)
- 「요구사항 템플릿」대로 `### 요구사항 {n}: {이름}` 을 반복한다

### 필요한 결정 상세

- 그룹 문자로 묶는다 (예: A 할인 규칙, B 가입·인증, C 정산, D 범위, E 외부 요청). 그룹마다 결정 5개 이하
- 결정마다
    - 무엇을 정하는가 한 문장
    - 구체 예시: 옵션마다 결과가 어떻게 달라지는지 숫자로 (예: 한도 1,500원, 라떼 2잔 → 잔마다 3,000원, 줄마다 1,500원)
    - 옵션 a/b/c 와 트레이드오프 한 줄씩. 마스터가 "A1. a" 로 답할 수 있게 한다
    - 추천안: `@초안 a안 — {근거}`
    - LLM 이 알 수 없는 것(가격 정책, 계약 조건, 외부 합의)은 추천 없이 `@미정 — {이유 한 줄}`
- 날짜 윈도우는 경계 날짜 예시로 포함/미포함을 묻는다. 수치 윈도우는 이상/이하/초과/미만을 묻는다. 금액은 소수점 정밀도와 반올림을 묻는다

### 기존 시스템과 맞닿는 곳

- 코드에서 확인한 사실: `@사실 ({경로})` 와 이 기능에 주는 뜻
- 구현 전에 확인해야 할 위험 (예: 기존 정산이 새 할인분까지 지급하는가)
- 범위 밖 목록과 별개 작업으로 나눌 것

## 요구사항 템플릿

마스터가 템플릿을 주지 않았을 때 쓴다.

```markdown
### 요구사항 2: 메뉴 가격 변경

**사용자 스토리:** 점주로서, 메뉴 가격을 바꿔서 원가 변동에 대응하고 싶다.

**인수 조건**
1. WHEN 점주가 가격을 저장하면, THE System SHALL 변경된 가격을 메뉴판에 표시한다. @결정
2. IF 가격이 0원 이하이거나 숫자가 아니면, THEN THE System SHALL 저장을 거부하고 사유를 표시한다. @초안
3. WHILE 메뉴가 '품절' 상태인 동안, THE System SHALL 가격 변경은 허용하되 주문은 받지 않는다. @초안 (A2)

**업무 규칙** (EARS 대신 표)
| 사이즈 | 가격 규칙 | 표기 |
|---|---|---|
| Regular | 기준가 | @결정 |
| Large | 기준가 + 500원 | @초안 (A3) |

**범위 밖:** 지점별 다른 가격 (다음 단계)
```

- 사용자 스토리: `{역할}로서, {행동}해서 {얻고 싶은 것}하고 싶다.` 역할은 운영자·점주·고객처럼 실제 사람이다
- 인수 조건: EARS 키워드만 영어 대문자로 쓰고 나머지는 한국어다
    - 항상 → `THE System SHALL …`
    - 사건 → `WHEN …, THE System SHALL …`
    - 상태 → `WHILE …, THE System SHALL …`
    - 예외·실패 → `IF …, THEN THE System SHALL …`
    - 선택 기능 → `WHERE …, THE System SHALL …`
    - 조건 하나에 응답 하나. 응답이 둘이면 조건을 나눈다
    - 끝에 마커 하나, 걸린 결정이 있으면 괄호에 ID
- 업무 규칙: 값 대응, 계산식, 경계 예시처럼 EARS 문장으로 쓰면 길어지는 규칙. 경계는 양쪽 예시 행을 둔다 (예: 한도 1,500원 → 1,500원 할인됨, 1,501원 거부)
- 범위 밖: 마스터가 다음 단계로 미룬 것, 비슷해 보이지만 하지 않는 것

## 마커

모든 인수 조건, 업무 규칙 행, 원칙 문장에 마커 하나를 붙인다.

- @결정: 마스터 문장을 그대로 옮긴 것
- @해석: 마스터 문장이 짧아 LLM 이 풀어 쓴 것. 풀어 쓴 내용을 함께 적는다
- @초안: 마스터 문장이 없어 LLM 이 채운 것. 가장 틀리기 쉽다
- @미정: LLM 이 채울 수 없는 것. 이유 한 줄
- @사실: 코드·실행 결과로 이번 작업에서 확인한 것. 출처 경로를 붙인다
- @가정: 확인하지 않고 참으로 둔 것. 그 위에 쓰는 요구사항은 "X 이면 A, Y 이면 B" 로 나눠 쓴다

해석이 3개 이상 얽혀야 초안을 쓸 수 있으면, 쓰기 전에 그 해석들을 마스터에게 먼저 확인받는다.

## 답 반영

마스터가 "A1. 임직원 할인 = 제휴회사", "B4. A안", "C3. C2" 처럼 답하면 같은 문서를 고친다. 새 문서를 만들지 않는다.

- 답 하나마다 그 결정에 걸린 인수 조건·업무 규칙·흐름 그림·결론을 모두 찾아 고친다. 결정 ID 로 문서를 검색해 빠뜨리지 않는다
- 반영한 자리의 마커를 `@확정 ({YYYY-MM-DD} "{답 원문}")` 으로 바꾼다
- "C2" 처럼 다른 답을 가리키거나 짧은 답을 풀어 쓴 것은 @확정 이 아니라 @해석 이다
- 답 때문에 임시 이름이 확정되면 문서 전체에서 임시 이름을 바꾸고, 남지 않았는지 검색한다
- 「필요한 결정 상세」 맨 위에 결정 기록을 둔다: 결정 ID, 마스터 답 원문, 문서에 반영한 뜻
- 답 때문에 새로 생긴 빈 곳은 다음 번호로 결정을 추가한다 (예: A6, A7)
- 메모리에 문서 위치를 남겼으면 확정 결정과 남은 결정을 갱신한다

## 끝맺음

- 첫 줄: 다음에 답할 결정 하나. 구체 예시와 추천안을 붙인다 (예: "A6 에 답해 주세요. 한도 1,500원에 라떼 2잔을 한 줄로 주문하면, 잔마다 세면 3,000원, 줄마다 세면 1,500원이 할인됩니다. 추천은 잔마다입니다.")
- 둘째 줄: 문서 경로(클릭 가능한 `path`) 또는 문서 링크
- 무엇을 썼는지·바꿨는지 불릿 5개 이하. 문서 내용을 채팅에 다시 늘어놓지 않는다
- 남은 결정 개수와 먼저 정할 결정 ID
- 원문에 없던 새 발견이나 구현 전 확인할 위험은 3개 이하, 한 줄씩

## 하지 않는 것

- 코드를 바꾸지 않는다
- 경로를 정하기 전에 마크다운 파일을 쓰지 않는다
- 공유 문서 경로에서 조사를 다 마친 뒤 문서를 한 번에 만들지 않는다. 뼈대가 조사보다 먼저다
- 마스터가 정한 용어 정의를 다듬어 바꾸지 않는다. 문제가 있으면 결정 항목으로 올린다
