# sdd-brief — 모두가 읽는 기획 문서

설명 한 덩어리를 받아, 코드를 읽지 않는 직원도 이해하고 의견을 낼 수 있는 기획 문서를 쓴다. 코드는 바꾸지 않는다.

정해진 원칙은 셋이다. 모든 규칙은 이 셋에서 나온다.

- 개발 요소를 제외하고 기획 요소만 담는다
- 다른 직원(비개발자 포함)들이 모두 이해할 수 있도록 쓴다
- 기존의 AS-IS 를 친절한 플로우, 가능하면 아주 이해하기 쉬운 유저시나리오로 대체한다

`~/.claude/skills/sdd-draft/references/spec-format.md` 에서 「한 번만 쓴다」「필요한 결정」「답 반영」만 읽고 따른다. 「마커」와 「요구사항 템플릿」의 EARS 는 개발 요소라서 따르지 않는다. 대신 이 문서의 「결정 쓰는 법」「해야 할 일 쓰는 법」을 따른다.

- `sdd-draft`: 같은 기능의 개발자용 요구사항 문서. 이 스킬의 결정을 원본으로 삼고, 결정 ID 로 가리킨다
- `sdd-design`: 같은 기능의 design.md (어떻게 만드는가)
- `sdd-quick`: 문서 없이 채팅으로 쓰는 작은 스펙

## 형식 고르기

- 설명에 "artifact", "아티팩트" 로 만들라는 말이 있다 → 「공유 문서 경로」
- 없다 → 「마크다운 경로」. 읽는 사람이 직원이어도 마크다운이다

형식을 가리키는 말은 떼고, 나머지를 설명으로 쓴다.

## 설명 읽기

설명에서 아래를 뽑는다. 없는 것은 비워 두고 초안에서 채운다.

- 기능 이름 하나 (예: 제휴카페). 문서 제목은 `{기능} 기획 문서`
- 마스터가 정의한 용어: 정의 문장을 그대로 옮긴다. 고치지 않는다
- 목적과 정해진 원칙: 마스터 문장 하나에 원칙 하나
- 마스터가 기획서 양식을 주면 그 양식이 「절 구성」보다 우선한다
- 저장 경로: 경로처럼 보이는 문자열(`docs/…`, `*.md`, 폴더)

설명이 비어 있으면(무엇을 만들지 없음) 쓰지 말고 무엇의 기획 문서인지 한 번 묻는다.

## 마크다운 경로

### 저장 경로 정하기

기획 문서는 그 기능의 요구사항 문서·design.md 와 같은 폴더에 `brief.md` 로 둔다. 경로가 정해지기 전에는 파일을 쓰지 않는다.

- 설명에 경로가 있다 → 그 경로. 폴더면 그 안의 `brief.md`
- 없으면 현재 리포의 `origin/main` 에서 같은 기능의 폴더를 찾는다: `git ls-tree -r --name-only origin/main | grep -E '(^|/)(requirements|design|brief)\.md$'`
    - 기능 이름과 맞는 폴더가 정확히 하나다 → 그 폴더. 쓰기 전에 채팅에 "{경로}에 씁니다" 한 줄을 남긴다
    - 없다 → 기본값 `.claude/specs/{slug}/brief.md`. 쓰기 전에 같은 한 줄을 남긴다
    - 둘 이상이다 → `AskUserQuestion` 한 번으로 묻는다. 찾은 후보와 기본값을 옵션으로 주고, 추천안을 첫 옵션에 둔다
- `slug` 는 기능 이름의 영어 kebab-case 50자 이내 (예: `partner-cafe`)
- 같은 파일이 이미 있으면 덮어쓰기 전에 읽고, 갱신인지 새 파일인지 한 번 묻는다
- 마스터가 요청하기 전에는 이 파일을 커밋하지 않는다

### 쓰는 순서

- **뼈대 먼저.** Write 로 제목, 기준 날짜, 「절 구성」의 `## 절` 헤딩, 절마다 `(작성 중)` 한 줄을 만든다
- 「조사」를 한다
- Edit 로 절 하나씩 채운다. 절 하나를 채울 때마다 채팅에 "지금 {절} 작성 중" 한 줄을 남긴다
- 「정해야 할 것」은 마지막에 채운다. 다른 절을 쓰면서 드러난 빈 곳이 모여야 쓸 수 있다
- 「쉬운 말 점검」을 한다
- `(작성 중)` 이 남았는지 검색해 없앤다

### 마크다운 형식

- 표는 「해야 할 일」의 업무 규칙에만, 숫자 목록은 확인 목록에만 쓴다. 나머지는 2단 불릿
- 흐름 그림은 ```mermaid `flowchart LR` 블록. 노드 라벨에 예시 숫자를 넣고, 그림 아래에 읽는 법 한두 문장. 그림 제목은 주제가 아니라 결론 문장이다

## 공유 문서 경로

`spec-build-artifact` 의 「도구 확인」「Docs 경로」「대체 경로」를 그대로 따른다. 다른 점만 적는다.

- 뼈대의 `pending` 블록은 「절 구성」의 절마다 하나다. `intent` 에 절 이름과 들어갈 내용을 적는다
- 흐름 그림은 widget 다이어그램으로 그리고 screenshot 으로 확인한다
- 표는 어디든 써도 된다. 문서 화면이 표를 그려 주기 때문이다
- 다 채우면 문서 링크를 프로젝트 메모리에 `reference` 로 남긴다. 결정 내용은 메모리에 옮기지 않는다

## 조사

조사는 지금 이야기를 쓰고, 결정을 끌어내는 데 필요한 만큼만 한다.

- `git fetch` 후 `origin/main` 기준으로 읽는다
- 코드는 "지금 이 일이 어떻게 돌아가는가" 를 알아내는 데만 쓴다. 알아낸 것은 지금 이야기로 옮기고, 코드 경로·테이블 이름은 문서에 쓰지 않는다
- 같은 폴더에 요구사항 문서나 design.md 가 이미 있으면 읽고, 이미 정해진 것과 부딪히는 곳을 열린 결정으로 올린다
- 확인하지 못한 사실은 이야기에 쓰지 않는다. 「정해야 할 것」의 열린 결정으로 올린다
- 마스터 문장끼리 부딪히는 곳을 찾는다. 같은 말이 문장마다 다른 뜻이면 열린 결정으로 올린다

## 담을 것과 뺄 것

- 담는다
    - 필요한 결정: 옵션, 예시, 추천안
    - 용어 뜻
    - 목적, 참여자, 정해진 원칙
    - 지금 이야기, 바뀐 뒤 이야기, 흐름 그림
    - 사용자 스토리, 확인 목록, 업무 규칙, 범위 밖
- 뺀다
    - 결정 표기(`@결정`·`@초안`·`@해석`·`@미정`·`@사실`·`@가정`·`@확정`)
    - EARS 문장(`WHEN …, THE System SHALL …`)
    - 코드 경로, 테이블, API, 코드 근거
    - 구현 위험, 별개로 나눌 개발 일

설명이나 조사 결과에 뺄 것이 섞여 있으면 문서에 쓰지 않는다. 끝맺음에 "요구사항이면 `sdd-draft`, 설계면 `sdd-design` 으로 넘길 것" 으로 한 줄씩 적는다.

## 쉬운 말

- 모든 문장을 일상에서 쓰는 말로 쓴다. 기술용어를 쓰지 않는다
- 업무 용어(예: 정산, 사원증 인증)가 꼭 필요하면 「쓰는 말」 절에 한 문장 뜻을 적고, 본문에서는 그 이름만 쓴다
- 금액·날짜·횟수는 실제 숫자로 쓴다. "일정 금액", "정해진 기간" 을 쓰지 않는다
- 쓸 때 참고하는 바꾸기 예시
    - "API 호출이 실패하면" → "화면에서 저장이 안 되면"
    - "레코드를 생성한다" → "목록에 한 줄이 새로 생긴다"
    - "배치로 정산한다" → "매달 1일에 한 번에 모아 계산한다"
    - "권한이 없으면" → "이 화면을 볼 수 없는 직원이면"

## 쉬운 말 점검

다 쓴 뒤, 끝맺음을 보내기 전에 한다. 예시 목록으로 점검하지 않는다. 목록 밖의 말을 놓치기 때문이다.

- `Agent` 로 하위 에이전트 하나를 띄운다. 넘기는 것은 문서 경로(또는 링크)와 아래 역할뿐이다. 이 대화의 맥락은 넘기지 않는다. 맥락을 알면 모르는 말도 알아듣기 때문이다
    - 역할: "당신은 코드를 읽지 않는 운영 담당 직원이다. 이 문서를 처음부터 끝까지 읽고, 뜻을 모르겠거나 두 가지로 읽히는 말을 문장과 함께 목록으로 돌려 달라. 고치지는 말라."
- 돌려받은 말을 「쉬운 말」 규칙으로 고친다
- 고친 문장이 5개 이상이면 한 번 더 점검한다. 점검은 최대 두 번이다

## 절 구성 (이 순서)

해당 없는 절은 지우지 말고 "해당 없음 — {이유 한 줄}" 로 남긴다. 요약·결론 절은 두지 않는다.

### 정해야 할 것

- 「열린 결정」과 「정해진 결정」 두 하위 절. 맨 위에 두는 이유는 마스터가 가장 먼저 할 일이기 때문이다
- 모양은 「결정 쓰는 법」을 따른다
- 결정이 모두 정해지면 「열린 결정」은 "없음" 한 줄이 된다

### 쓰는 말

- 용어마다 뜻 한 문장
- 마스터 정의는 원문 그대로 옮긴다. LLM 이 새로 붙인 이름은 "새로 붙인 이름" 이라고 밝힌다
- 용어끼리 부딪히는 곳은 어느 문장과 어느 문장이 다른지 인용만 하고 결정 ID 로 가리킨다

### 무엇을, 왜

- 목적 한 문장
- 참여자: 누가, 무엇을 하는지, 돈·물건·정보가 어떻게 오가는지
- 정해진 원칙: 마스터 문장을 불릿 하나씩

### 이야기

AS-IS 를 대신하는 절이다. 표나 단계 목록이 아니라 이야기로 쓴다.

- 지금 이야기: 기능이 생기기 전 인물이 겪는 일. 새 기능이면 "지금은 이렇게 한다" 를 쓴다
- 바뀐 뒤 이야기: 기능이 생긴 뒤 같은 인물이 같은 장면에서 겪는 일
- 이야기마다 이름 있는 인물 한 명, 장소 한 곳, 실제 숫자 하나 이상. 3~6문장. 인물 이름은 실제 직원 이름이 아니라 지어낸 이름
- 지금 1개 + 바뀐 뒤 1개가 기본이다. 인물 종류가 다르면(예: 고객, 점원) 인물마다 한 쌍
- 아직 정하지 않은 규칙이 이야기에 나오면 짐작으로 채우지 않고 결정 ID 를 가리킨다
- 흐름 그림은 이야기 뒤에 하나. 예시 숫자는 그림 한 곳에만 둔다

예시 (제휴카페):

```markdown
- 지금 이야기
    - 김민지 대리는 점심을 먹고 회사 1층 '빈카페'에서 아메리카노 한 잔을 산다. 값은 5,900원이다. 김 대리는 계산대에서 5,900원을 모두 낸다.
- 바뀐 뒤 이야기
    - 다음 날 김 대리는 같은 아메리카노를 고르고 계산대에서 사원증을 보여 준다. 점원이 화면에서 '제휴회사 직원' 버튼을 누르자 1,500원이 빠지고, 김 대리는 4,400원을 낸다. 라떼 두 잔을 한 번에 사면 몇 원이 빠지는지는 A6 에서 정한다.
```

### 해야 할 일

- 첫 문장: 해야 할 일의 개수와 각각 어디서 나왔는지 (마스터 문장, 빈 곳)
- 「해야 할 일 쓰는 법」대로 `### 해야 할 일 {n}: {이름}` 을 반복한다

## 결정 쓰는 법

포맷 문서의 「필요한 결정」과 같다. 결정 표기만 쉬운 말로 바꾼다.

- 열린 결정
    - `**A1. {무엇을 정하는가}**` 한 문장
    - 예시: 옵션마다 결과가 어떻게 달라지는지 숫자로
    - 옵션 a/b/c 와 장단점 한 줄씩. 마스터가 "A1. a" 로 답할 수 있게 한다
    - `추천: a안 — {근거}`. LLM 이 알 수 없는 것(가격 정책, 계약 조건, 외부 합의)은 `추천 없음 — {이유 한 줄}`
    - `걸린 곳: 해야 할 일 2, 이야기`. 답을 반영할 자리를 이 목록으로 찾으므로 빠짐없이 적는다
- 정해진 결정
    - `**A1. {무엇을 정했는가}**` 한 문장
    - `답: {YYYY-MM-DD} "{답 원문}"`. 짧은 답을 풀어 썼으면 `풀어 쓴 뜻: …` 을 붙이고 끝맺음에서 맞는지 묻는다
    - `반영한 곳: …`. 반영한 규칙 내용은 다시 쓰지 않는다
    - 옵션, 예시, 추천 근거는 지운다

## 해야 할 일 쓰는 법

```markdown
### 해야 할 일 2: 메뉴 가격 바꾸기

**사용자 스토리:** 점주로서, 메뉴 가격을 바꿔서 원두값이 오른 만큼 반영하고 싶다.

**확인 목록**
1. 점주가 가격을 저장하면, 메뉴판에 바뀐 가격이 바로 보인다.
2. 가격이 0원 이하이면, 저장되지 않고 "가격은 1원 이상이어야 합니다" 가 보인다.
3. 메뉴가 '품절' 인 동안에는, 가격은 바꿀 수 있지만 주문은 받지 않는다.

**업무 규칙**
| 크기 | 가격 |
|---|---|
| 보통 | 기준 가격 |
| 큰 컵 | 기준 가격 + 500원 |

**범위 밖:** 지점마다 다른 가격 (다음 단계)
```

- 사용자 스토리: `{역할}로서, {행동}해서 {얻고 싶은 것}하고 싶다.` 역할은 점주·고객·운영 담당처럼 실제 사람이다
- 확인 목록: "~하면, ~된다" 한 문장에 조건 하나, 결과 하나. 결과가 둘이면 줄을 나눈다. 문장 끝에 아무 표기도 붙이지 않는다
- 업무 규칙: 값 대응, 계산식, 경계 예시처럼 문장으로 쓰면 길어지는 규칙. 경계는 양쪽 예시 행을 둔다 (예: 한도 1,500원 → 1,500원 할인됨, 1,501원 거부)
- 범위 밖: 다음 단계로 미룬 것, 비슷해 보이지만 하지 않는 것

## 답 반영

포맷 문서의 「답 반영」대로 같은 문서를 고친다. 새 문서를 만들지 않는다. 다른 점만 적는다.

- 고칠 자리는 그 결정의 「걸린 곳」 목록으로 찾는다. 본문에 결정 표기가 없기 때문이다
- 고친 자리에는 아무 표기도 붙이지 않는다. 답 원문은 「정해진 결정」의 그 ID 자리 한 곳에만 둔다
- 직원 의견이 정해진 결정과 다른 말을 하면, 결정을 고치지 않고 다음 번호의 열린 결정으로 올린다

## 끝맺음

- 첫 줄
    - 열린 결정이 있으면: 다음에 답할 결정 하나. 구체 예시와 추천안을 붙인다
    - 열린 결정이 없으면: 개발자용 요구사항 문서를 쓰는 다음 명령 한 줄 (예: `/sdd-draft .claude/specs/partner-cafe/brief.md`)
- 둘째 줄: 문서 경로(클릭 가능한 `path`) 또는 문서 링크
- 무엇을 썼는지·바꿨는지 불릿 5개 이하. 문서 내용을 채팅에 다시 늘어놓지 않는다
- 문서에서 뺀 개발 요소가 있으면 "넘길 것" 으로 한 줄씩, 3개 이하
- 쉬운 말 점검에서 고친 문장 수 한 줄

## 하지 않는 것

- 코드를 바꾸지 않는다
- 경로를 정하기 전에 마크다운 파일을 쓰지 않는다
- 설명에 아티팩트 요청이 없는데 공유 문서로 만들지 않는다
- 공유 문서 경로에서 조사를 다 마친 뒤 문서를 한 번에 만들지 않는다. 뼈대가 조사보다 먼저다
- 마스터가 정한 용어 정의를 다듬어 바꾸지 않는다. 문제가 있으면 열린 결정으로 올린다
- 같은 기능의 요구사항 문서나 design.md 를 함께 쓰지 않는다
