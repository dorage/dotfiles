# 검토용 스펙 계약서

`spec-build-md` 와 `spec-build-artifact` 가 함께 쓰는 단일 출처다. 두 스킬은 "어디에 쓰는가" 만 다르고, "무엇을 조사해 무엇을 쓰는가" 는 이 문서를 따른다.

## 읽는 사람

- 작업자가 아니다. **작업을 검토하고 진행 방향을 정하는 사람**이다. 그 사람이 이 문서만 읽고 승인·보류·조건부 승인을 결정할 수 있어야 한다.
- 작업 기억이 작다(ADHD). 화면에 없는 것은 잊힌다. 앞 절을 기억해야 뒤 절이 이해되는 구조를 만들지 않는다.
- 그래서 결정할 것을 맨 앞에 두고, 각 절의 첫 문장이 그 절의 결론이다.

## 입력 해석

요청에서 대상을 찾는다.

- PR 번호(`#1063`, `1063`) → `gh pr view {n} --json title,body,state,headRefName,files,commits,comments,reviews` 와 브랜치 diff
- 이슈 번호 → `gh issue view {n} --json title,body,comments` 와 연결된 PR
- 브랜치 이름 → `git diff $(git merge-base origin/main {branch}) {branch}`
- 계획 텍스트·파일 경로 → 그 내용과 거기서 가리키는 코드
- 대상이 없거나 둘 이상으로 읽히면 `AskUserQuestion` 한 번으로 확인한다

## 조사 절차

- 조사 전에 `git fetch` 로 원격 최신 상태를 맞춘다
- PR·이슈 본문과 **모든 사람 댓글**을 끝까지 읽는다. 결정은 본문보다 댓글에 있는 경우가 많다. 봇 댓글(terraform plan, CI)은 결과 한 줄만 본다
- 본문이 길면(수십 KB) 스크래치패드에 저장하고 나눠 읽는다. 앞부분만 보고 쓰지 않는다
- diff 에서 핵심 파일을 직접 읽는다: 스키마·마이그레이션, 설정·환경변수, 진입점(handler/router/CLI), 도메인 규칙, 인프라
- 본문의 주장을 코드로 확인한다. 확인한 것과 못 한 것을 구분해 적는다
- CI 상태(`gh pr checks {n} --json name,state`), 머지 가능 여부, 연결된 이슈의 열림/닫힘을 확인한다
- 새로 추가된 테스트 이름을 뽑아 테스트 커버리지를 판단한다: `git diff ... -- '*test_*' | grep -E '^\+\s*(async )?def test_'`
- **반대편에서 한 번 더 읽는다.** 원문에 틀린 서술이 있는지 찾는다. 예: "timeout 을 올리면 된다" 인데 플랫폼 최댓값이 이미 그 값인 경우, "다음 날 자동 복구된다" 인데 경계의 하루는 복구되지 않는 경우. 찾은 것은 문서에 "이 문서를 쓰며 새로 짚은 점" 으로 표시한다

## 절 구성 (이 순서)

해당 없는 절은 지우지 말고 "해당 없음 — {이유 한 줄}" 로 남긴다. 검토자가 "빠뜨렸나?" 를 묻지 않게 하기 위해서다.

### 검토자가 내릴 결정

- 첫 문장: 머지·진행을 승인해도 되는지와 진짜 결정이 무엇인지
- 결정마다: 무엇을 정하는가, 추천안, 근거(코드 경로·CI 결과·원문 인용)
- 추천안이 없는 결정(기획·정책)은 "개발 쪽 추천안 없음, {누가} 확인" 으로 적는다
- 5개를 넘기지 않는다. 넘으면 묶는다

### 배경과 변경 요약

- 왜 필요한가 (문제)
- 바뀌는 것: 전 → 후
- 안 바뀌는 것 (검토자가 걱정할 만한 자리 위주)
- 지금 상태: PR 상태, 브랜치, 최신 커밋, 배포 여부, 출처 링크

### 불변식

- 날짜 윈도우 → 구체 날짜 예시로 **포함/미포함**을 경계 양쪽에 걸쳐 보인다 (예: lag 0·1·7·8)
- 수치 윈도우 → 최소/최대/이상/이하/초과/미만을 명시한다
- 금액·정산 → 컬럼 타입과 소수점 정밀도, 계산식이 바뀌는지
- 멱등·중복 → 어떤 유니크 키·코드 검사가 막는지, 막지 못하는 구멍
- 실패 방향 → 덜 주는가, 두 번 주는가, 조용한가, 시끄러운가

### DB 쿼리

- 스키마 변경: up/down SQL 원문, 온라인 DDL 여부, 운영 행 수 확인 여부
- 바뀐 읽기·쓰기 쿼리: 전 → 후 SQL, 왜 바꿨는지, 실행 계획 확인 여부
- 호출 횟수가 바뀌는 쿼리
- 검토자가 배포 전에 돌릴 운영 확인 쿼리와 통과 기준

### 실행 인터페이스

있는 것만: REST API(메서드·경로·요청·응답 예시·에러), CLI(명령 예시), 람다(스케줄, 수동 invoke 페이로드, 응답 모양), 환경변수(이름·기본값·허용 범위·되돌림 값), 입력 우선순위.

### 플로우차트

- 분기·반복·실패 경로가 보이는 흐름. 제목은 주제가 아니라 결론 문장이다
- 그림 아래 한두 문장으로 읽는 법을 적는다

### 테스트 시나리오

Gherkin 으로 쓰고 셋으로 나눈다. Gherkin 작성 규칙은 `spec-bdd` 스킬을 따른다.

- 자동 테스트가 있는 시나리오 (어느 테스트가 덮는지)
- 운영에서만 확인할 수 있는 시나리오 (확인 쿼리·명령과 통과 기준 포함)
- 테스트가 없는 자리 (왜 없는지, 위험도)

### 추가 검토사항

- 성능: 제한값과 예상치를 숫자로. 근거 기록의 위치
- 보안: 새 권한·시크릿·외부 호출, 수동 경로로 우회 가능한 안전장치
- 운영: 알람, 재시도·DLQ, 동시 실행, 배포 당일 예상되는 알람
- 사용자에게 보이는 변화: 화면·금액·알림
- 롤백: 층마다(설정·인프라·스키마·데이터·코드) 되돌리는 방법과 걸리는 시간

### 결정 기록

ADR 형식. 결정마다: 상태(누가 언제 결정 / 계획 단계 결정 / 미결), 맥락, 결정, 버린 안과 버린 이유. 원문 위치를 첫 문장에 적는다.

### 배포 단계와 열린 질문

- 배포 단계: 단계마다 할 일, 통과 기준, 되돌림
- 성공 판단 기준: 켠 뒤 무엇을 보면 성공인지. 비즈니스 효과를 재는 지표가 있으면 적고, 기준값이 없으면 "아직 안 쟀다" 고 적는다
- 원문에서 고쳐야 할 서술
- 열린 질문: 체크박스(`- [ ]`), 질문마다 누가 답할지

## 문장 규칙

- 각 절의 첫 문장이 결론이다. "이 절은 ~를 설명한다" 로 시작하지 않는다
- 문장은 25단어 미만, 문단은 3문장 이하, 모든 문장은 자기완결적
- 테이블 금지 → 2단 불릿. 숫자 목록 금지 → 불릿 ("단계 1 —" 처럼 라벨로 순서를 준다)
- 단정 앞에는 출처(파일 경로, 커밋, 원문 인용, CI 결과)
- 확인한 것과 확인하지 못한 것을 섞지 않는다. 못 한 것은 "확인하지 않았다" 로 적는다
- 상태 숫자("N건", "N개 통과")는 이번 조사에서 실제로 본 값만 쓰고, 기준 날짜를 붙인다
- 가정이 3개 이상 얽히면 쓰기 전에 마스터에게 가정을 확인받는다

## 끝맺음

- 채팅 응답 첫 줄: 결과물 링크 또는 경로
- 원문에 없던 새 발견이 있으면 최대 3개만, 한 줄씩
- 마지막 줄: 마스터가 2분 안에 할 수 있는 다음 행동 하나
- 문서 내용을 채팅에 다시 요약하지 않는다
