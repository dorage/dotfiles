# spec-build-md — 검토용 스펙, 마크다운 파일

먼저 `~/.claude/skills/spec-build/references/spec-contract.md` 를 읽는다. 무엇을 조사하고 어떤 절을 쓰는지는 전부 그 문서를 따른다. 이 스킬은 "어디에 어떻게 쓰는가" 만 정한다.

## 파일 위치

- 요청에 경로가 있으면 그 경로
- 없으면 현재 작업 디렉터리의 `.claude/specs/{YYYY-MM-DD}-{slug}.md`
    - `slug` 는 영어 kebab-case, 대상이 PR 이면 `pr-{번호}-{짧은-설명}` (예: `2026-09-29-pr-1063-settlement-rolling-window.md`)
    - git 리포 안이면 이 파일은 커밋하지 않는다. 마스터가 요청할 때만 커밋·PR 댓글로 올린다
- 같은 대상의 파일이 이미 있으면 덮어쓰기 전에 읽고, 갱신인지 새 파일인지 한 번 묻는다

## 절차

- 스펙 계약서의 「입력 해석」과 「조사 절차」대로 조사한다
- 계약서의 절 순서대로 한 파일에 쓴다. 파일 머리에 제목(`# {대상} 검토 스펙`), 기준 날짜, 출처 링크를 둔다
- 긴 문서는 절 단위로 나눠 쓴다: Write 로 뼈대(제목 + `## 절` 헤딩 + 절마다 `(작성 중)` 한 줄)를 먼저 만들고, Edit 로 절마다 채운다. 절 하나를 채울 때마다 채팅에 "지금 {절} 작성 중" 한 줄을 남긴다
- 다 쓰면 「(작성 중)」 이 남았는지 검색해 없앤다

## 마크다운 형식 규칙

- 테이블 금지 → 2단 불릿
- 숫자 목록 금지 → 불릿. 순서는 "단계 1 —" 같은 라벨로 준다
- 헤딩은 인용할 가치가 있는 단위에만 쓴다 (`##` 절, `###` 하위 항목)
- 플로우차트는 ```mermaid `flowchart TD` 블록으로 그린다
    - 노드 라벨은 한 줄 20자 안팎, 줄바꿈은 `<br/>`
    - 실패 경로는 `classDef bad stroke:#d33` 같은 클래스로 구분하고, 강조 노드는 하나만
    - 그림 아래에 읽는 법 한두 문장
- 테스트 시나리오는 ```gherkin, SQL 은 ```sql, 요청·응답은 ```json, 명령은 ```bash 블록
- 열린 질문은 `- [ ]` 체크박스

## 끝맺음

계약서의 「끝맺음」을 따른다. 첫 줄은 파일 경로(클릭 가능한 `path` 형식)다. 마지막 줄에 PR 댓글로 올릴지 한 줄로 제안한다 (예: "다음: `gh pr comment 1063 -F {경로}` 로 올릴까요?").
