# spec-impl — 스펙 → 테스트 → 구현

구현은 이 스킬 안에서만 한다. 순서는 스펙, 테스트, 구현이다. 앞 단계가 끝나지 않으면 다음 단계로 가지 않는다.

## 적용 범위

- 적용: 동작이 바뀌는 코드의 생성과 수정 (기능 추가, 버그 수정, 동작이 바뀌는 리팩터링)
- 제외: 문서(`.md`), 스펙 파일(`.feature`) 작성, 동작이 그대로인 이름 변경과 포맷 정리, 설정값 한 줄 변경

## 스펙 찾기

요청에서 스펙을 찾는다. 아래 순서로 보고, 처음 찾은 것을 쓴다.

- 요청에 PR·이슈 번호가 있다 → `gh pr view {번호}` 또는 `gh issue view {번호}` 본문과 연결된 스펙 링크
- 요청에 claude.ai artifact 링크가 있다 → 그 문서 (spec-build 산출물)
- 리포지토리에 관련 `*.feature` 파일이 있다 → 그 파일

스펙이 없으면 구현하지 않는다.

- `Skill(skill="spec-bdd", args="{요청}")` 으로 시나리오를 먼저 만든다
- 만든 시나리오를 마스터에게 보여 주고 확인받은 뒤 다음 단계로 간다

스펙이 있어도 아래면 멈추고 마스터에게 묻는다.

- 구현할 시나리오에 `@미정` 이 있다 → 그 시나리오는 구현하지 않고 **필요한 결정** 목록에 올린다
- `@초안`, `@해석` 시나리오는 구현하되, PR 본문의 **필요한 결정** 목록에 올린다

## 작업 환경

- `git fetch` 후 뒤처졌으면 `git pull`
- `./.worktrees` 아래 worktree 를 만든다 (브랜치 `<type>/<short-description>`)
- 빈 커밋으로 draft PR 을 만든다. 이슈 기반이면 PR 본문에 이슈 번호를 넣는다

## 테스트 먼저

- 스펙의 시나리오 하나를 테스트 하나로 옮긴다. 테스트 이름에 시나리오 제목을 그대로 쓴다
- 프로젝트에 이미 있는 테스트 도구와 위치를 따른다. 테스트 도구가 없으면 도구 선택을 **필요한 결정** 으로 마스터에게 묻는다
- 테스트를 실행해 실패하는 것을 확인한다. 실패 출력 첫 줄을 남긴다
- 처음부터 통과하는 테스트는 시나리오를 제대로 옮기지 못한 것이다. 테스트를 다시 쓴다
- 테스트만 따로 커밋한다 (`test(...)`)

## 구현

- 실패한 테스트를 통과시키는 최소한의 코드를 쓴다
- 스펙에 없는 동작은 넣지 않는다. 필요해 보이면 "별개 작업입니다" 로 분리를 제안한다
- 구현 중 스펙이 틀렸다고 판단되면 테스트를 고치지 말고 멈춘 뒤 마스터에게 묻는다
- 전체 테스트를 실행해 새 테스트와 기존 테스트가 모두 통과하는 것을 확인한다
- 구현을 커밋한다 (`feat(...)`, `fix(...)`)

## 보고

PR 본문과 최종 답변에 아래를 남긴다.

- 시나리오 → 테스트 대응 목록 (시나리오 제목, 테스트 파일 경로:줄)
- 테스트 실행 명령과 결과 (통과 수 / 전체 수)
- 구현하지 않은 시나리오와 이유 (`@미정` 등)
- **필요한 결정** 목록

## 하지 않는 것

- 스펙 없이 구현하지 않는다
- 테스트보다 구현을 먼저 쓰지 않는다
- 테스트를 통과시키려고 테스트나 스펙을 몰래 고치지 않는다
