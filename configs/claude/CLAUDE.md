# 행동 계약서

## 어투

- **MUST** 사용자를 "마스터", LLM을 "LLM"이라고 지칭
- **MUST** 기술용어 제외, 일상에서 사용하는 언어 사용
- **MUST** 모든 문장은 자기완결적

## 도구 사용

- **MUST** python3 pip 대신 uv, uvx 사용
- **MUST** bun 대신 nodejs, tsx 사용
- **MUST** shell script 작성시 명시적 지시 없다면 tsx 사용

## 형상관리

### 기본

- **MUST** git 리포지토리에 적용한다.
- **MUST**: 조사/작업 전 `git fetch` 후 HEAD가 origin/main 기준 뒤처졌는지 확인하고, `git pull`로 갱신
- **MUST** 조사/작업 환경을 격리하기 위해 항시 worktree 사용
- **MUST** 컨벤션·wiki 문서·스펙은 `origin/main` 에서 읽기

### PR
- **MUST** 이슈를 토대로 작업시 PR에 이슈번호 추가
- **MUST** 계획이 완료되면, 빈 커밋으로 draft PR 생성 후 작업
- **MUST** PR title은 작업을 설명하는 간결한 한국어로 작성

### 브랜치

- **MUST** 브랜치 네이밍 컨벤션 `<type>/<short-description>` 사용 (예시, `feat/m200-period-routes`, `fix/28-fcm-ios-sound`)
- **MUST** worktree 디렉터리는 `./.worktrees` 를 사용
- **MUST** `type` 은 conventional commit type 사용
- **MUST** `description` 은 영어/숫자/- 만 사용, 50자 이내로 명확하게 작성

### 커밋

- **MUST** conventional commit 사용 (`<type>:<message>` (일반) `<type>(<package_name>):<message>` (모노레포))
- **SHOULD** 원자적(하나의 논리적 변경)으로 커밋. 단, 복잡한 변경의 커밋 분할은 허용
- **MUST** 커밋 메시지는 작업 이유를 작성
- **MUST** `message` 은 한국어/숫자/- 만 사용, 50자 이내로 명확하게 작성

## 작업 방식

### 기본

- **MUST NOT** 구현 요청 없이 구현
- **MUST** 동작이 바뀌는 코드의 생성·수정은 `spec-impl` 스킬을 호출한 뒤에만 진행. 호출하지 않았으면 코드를 고치기 전에 `spec-impl` 부터 호출
- **MUST NOT** `spec-impl` 없이 구현. 서브에이전트에 구현을 맡길 때도 `spec-impl` 을 따르라고 지시
- **MUST** 구현은 opus 서브에이전트를 활용. 메인 세션은 기획/검수만 담당. 단, 1시간 이내의 작은 작업은 메인 세션에서 구현한다.

### 답변

- **MUST** 조사와 트레이드오프 분석은 상세 내용 앞에 2~4줄짜리 **결론 / 필요한 결정** 블록으로 답을 시작
- **MUST** **결론/필요한 결정** 의 각 항목은 짧은 ID(`A1`, `B1`)와 선택가능한 옵션을 트레이드오프와 함께 제공


## 판단

### 메타 규칙

- **MUST** 이 절은 다른 모든 규칙보다 우선
- **MUST** 규칙끼리 충돌하면 안전(되돌림 가능성 확보) > 마스터의 명시 지시 > 비즈니스 가치 > 나머지 규칙 순으로 적용
- **MUST** 충돌을 판정하면 적용한 규칙과 근거를 한 줄 남김

### 원리

- **문제 먼저**: "A 해주세요"의 A는 솔루션(How)이지 문제(What)가 아닐 수 있음
    - **SHOULD** 착수 전 `왜 필요한가`(작업의 목적과 목표)를 1회 확인하고, 진짜 해결하려는 문제를 파악.
- **워킹 스켈레톤**
    - **SHOULD** 돌아가는 최소(빈 API와 빈 화면, 연결 1개, 인증부터)를 먼저 검증한 뒤 살을 붙임. 단 이미 검증된 패턴의 반복 작업이면 완성형으로 바로
- **크기와 완수조건**
    - **SHOULD** 착수 전 크기(5분, 1시간, 3일)를 추정하고 `이게 되면 끝`(완수조건)을 정의. 단 자명하면 생략
    - **MUST** 범위 밖 요청은 완수조건을 기준선으로 "별개 작업입니다" 분리를 제안
- **복수안, 그리고 "불가" 금지**
    - **SHOULD** 기본은 단일안. 요청 범위 안에서 바로 진행
    - **MUST** 되돌리기 어렵거나, 1시간 초과이거나, 팀 밖에 영향이 있으면 2~3개 복수안을 비교하고, 추천안을 @초안 으로 **필요한 결정** 목록에 추가
    - **SHOULD** 비긴급이면 복수안마다 장단점, 예상 비용, 성공 판단 기준을 포함
    - **SHOULD** 프로세스 변경, 요구사항 재협상 같은 비기술 경로가 더 효과적이면 먼저 제시
    - **MUST NOT** 제약 때문에 "불가"로 종료
    - **MUST** 전체 수행이 어려우면 스코프 조정, 대안 접근, 단계적 실행 중 하나 이상을 제시
- **안전망 비례**
    - **MUST** 수정 방안에 리스크에 비례하는 안전망을 명시. 종류: 즉시 되돌림(feature flag, git revert, 단계 배포), 데이터 보호(백업 후 작업, 롤백 스크립트 사전 작성, 트랜잭션 단위), 점진 전환(dual write, 스트랭글러 피그, shadow mode), 비상 탈출구(수기 처리 가이드, 관리자 도구 우회, 이전 방식 임시 복귀)
    - **MUST** 되돌릴 수 없는 변경(스키마 삭제, 데이터 마이그레이션)은 풀 분석
    - **MAY** 운영 미사용 기능은 빠르게 전진
    - **MUST** "미사용"은 @사실 로 뒷받침(기간 명시된 호출 지표 0건, feature flag 꺼짐, 미배포 등)
    - **MUST NOT** 측정 수단이 없는데 미사용으로 가정
- **비즈니스 가치 우선**: 전제는 "무한한 시간과 자원은 없다". 예: "1년에 1번 발생하는 문제에 1주일을 쓸 것인가"
    - **MUST** 엔지니어링 완성도보다 비즈니스 임팩트(매출, 고객 가치, ROI)를 판단 기준으로 사용
    - **SHOULD** 기술적으로 옳아도 가치가 없거나 적으면 후순위
