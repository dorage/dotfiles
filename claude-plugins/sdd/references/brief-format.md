# brief 포맷

`sdd:brief-dev`(개발자용)와 `sdd:brief-nondev`(비개발자용)가 함께 쓰는 단일 출처다. 두 스킬은 `sdd:draft` 가 쓴 요구사항 문서(requirements.md)를 받아, 결정 표기를 걷어 내 읽기 쉬운 기획 문서로 바꾼다. 새로 조사하거나 정하지 않는다. 요구사항 문서가 원본이고, brief 는 그 원본에서 뽑아낸 사본이다.

## 입력과 출력

- 입력: `sdd:draft` 가 쓴 `requirements.md` 하나
- 출력: 입력과 같은 폴더의 파일 하나
    - `sdd:brief-dev` → `brief-dev.md`
    - `sdd:brief-nondev` → `brief-nondev.md`
- 폴더 고르기와 덮어쓰기 확인은 `spec-format.md` 「저장 위치」를 따른다
- 마스터가 요청하기 전에는 커밋하지 않는다

## 변환 원칙

- 입력 문서의 모양을 그대로 둔다
    - 제목, 기준 날짜·작성자 줄, 절 순서, 헤딩 이름과 단계
    - 요구사항 번호, 인수 조건 번호와 개수, 결정 ID
    - 표, mermaid 그림, 공유 문서에서 옮겨 온 `[embedded content: …]` 자리
    - 맨 위 결론·요약 블록이 있으면 있는 그대로, 없으면 없는 그대로. 둘지 말지는 brief 가 정하지 않는다
- 내용을 더하지 않는다
    - 새 조사, 새 결정, 새 절, 새 예시, 이야기·인물·유저시나리오를 넣지 않는다
    - 결정마다 `예시:` 줄을 새로 붙이지 않는다. 예시는 입력에 있는 자리 하나에만 둔다 (`spec-format.md` 「한 번만 쓴다」)
    - 그림이 없으면 그림을 새로 그리지 않는다
- 내용을 빼는 것은 아래 「마커 제거」와 「개발 언어 순화」가 정한 것, 그리고 「참여자별 검토 기록」 절뿐이다. 이 절은 `sdd:persona-review` 가 다시 검토할 때 쓰는 LLM 용 기록이라 brief 로 옮기지 않는다 (`references/persona-review.md` 「검토 기록」)
- 문장을 나누거나 합치지 않는다. 한 줄은 한 줄로 바꾼다
- 마스터 답 원문(`"…"` 로 인용한 말)은 두 버전 모두 한 글자도 바꾸지 않는다

## 마커 제거

두 버전 모두 한다. 결정의 상태는 마커가 아니라 그 결정이 놓인 절(열린·남은 결정 / 정해진 결정·결정 기록)로 드러난다.

- 지우는 것
    - 마커 낱말: `@결정` `@해석` `@초안` `@미정` `@사실` `@가정` `@확정`
    - 마커에 붙은 날짜: `@확정 (A1, 11-02)` 의 `11-02`
    - 표의 「표기」 열
    - 마커만 설명하는 주석: `(모두 @결정)`, `(@가정 2개)`, `(@초안)`, `(모두 @사실)`
    - 마커만 설명하는 문장: "인수 조건 끝의 표기는 근거…", "아래 표는 같은 내용을 표기와 함께 적은 것입니다" 같은 것. 문장의 나머지 반이 여전히 맞으면 그 반은 남긴다 (예: "괄호 안 ID 는 걸린 결정입니다.")
- 남기는 것
    - 결정 ID: 괄호 하나로 모은다
        - `@확정 (A3, A7)` → `(A3, A7)`
        - `@해석 (A3), 한 잔 기준은 @확정 (A6)` → `(A3, A6)`
        - `@확정 (C2), C3·C5의 수기 처리는 @해석` → `(C2, C3, C5)`
        - ID 없이 마커만 있으면 아무것도 남기지 않는다
    - 마커 괄호 안의 내용 문장: `@가정 (기존 정책이 그대로면 …)` → `(기존 정책이 그대로면 …)`
    - 「표기」 열에 결정 ID 가 있었으면 그 ID 를 같은 행의 뜻·규칙 칸 끝에 `(A1)` 로 옮긴다
    - `@사실 ({경로})` 는 낱말만 지운다. 경로는 dev 에 남고, nondev 에서는 「개발 언어 순화」가 지운다
- 열린 결정의 추천안
    - `@초안 a안 — {근거}` → `추천: a안 — {근거}`
    - `@미정 — {이유}` → `추천 없음 — {이유}`
    - 옵션 줄 안의 `@초안` 은 그 옵션이 추천안이라는 뜻이다 → 줄 끝에 `(추천)`
    - 문장 안의 `(@초안 {내용})` → `(추천: {내용})`
    - 마스터가 "미정으로 두라" 고 답해서 붙은 `@미정 ({날짜} 답 …)` 은 추천이 없다는 뜻이 아니다 → `{날짜} 답으로 미정 …`. 옵션의 추천 표시는 그대로 둔다
- 정해진 결정의 답
    - `@확정 ({날짜} "{답}")` → `{날짜} 답 "{답}"`
    - 절을 옮기지 않는다. 「남은 결정」에 이미 정해진 결정이 섞여 있어도 그 자리에 두고 마커만 바꾼다
- 지운 뒤 빈 괄호, 겹친 쉼표, 줄 끝 공백을 정리한다

## 개발 언어 순화

`sdd:brief-nondev` 만 한다. 기준은 "개발자가 아닌 운영 직원이 읽을 수 있는가" 다. 업무 용어는 바꾸지 않는다. 헷갈리면 바꾸지 않는다.

- EARS 문장 → "~하면, ~된다" 문장
    - `WHEN …, THE System SHALL …` → "…하면, …된다."
    - `IF …, THEN THE System SHALL …` → "…이면, …된다."
    - `WHILE …, THE System SHALL …` → "…인 동안에는, …된다."
    - `THE System SHALL …` → "…된다." 또는 "…한다."
    - 한 줄은 한 줄이다. 번호와 개수가 입력과 같다. 둘째 문장이 있으면 같은 줄에 둔다
- 지우는 것
    - 코드 경로, 파일 이름, 테이블·컬럼 이름, API·핸들러 이름, 백틱으로 감싼 코드 조각
    - 코드 근거 블록 (예전 문서의 "지금 코드에서 확인한 것"). 업무 언어로 쓴 「지금 동작」 블록은 남긴다
    - 「기존 시스템과 맞닿는 곳」 표 칸에 남은 코드 이름과 "코드에서 확인했다" 문장. 표와 헤딩, 업무 언어로 쓴 지금 동작, 이번 범위 밖은 남긴다
    - 코드 조각을 지우면 반쪽이 남는 문장은 쉬운 반만 남긴다
    - 지운 블록을 가리키는 말 (예: "(아래 「지금 코드에서 확인한 것」 때문)")
- 바꾸는 말 (개발자만 읽는 말)
    - `M:N` → "여러 회사와 여러 카페를 서로"
    - "어드민" → "관리자 화면"
    - "(소프트 삭제)" 처럼 앞 문장을 개발 용어로 다시 부른 괄호 → 지운다
    - 문장 안의 "소프트 삭제" → "지우지 않고 남겨 두기" (그 기능의 업무 이름이 있으면 그 이름, 예: "퇴사 처리")
    - "피벗" → "묶어 보기" (예: "회사별·카페별로 묶어 볼 수 있게")
    - "레코드", "행" → "기록", "줄"
- 바꾸지 않는 말
    - 입력의 「도메인 언어」 절에 있는 용어 전부
    - 업무 용어: POS, 키오스크, 정산, D+6, KST, 선결제, 쿠폰, 스탬프, 세금계산서, 정가, 제휴가, 도메인(이메일 @ 뒤쪽) 같은 것
    - "LLM", "마스터": 마스터가 정한 호칭이다
    - 마스터 답 원문 (`"소프트딜리트"`, `"피봇팅"`, `"2-depth"` 처럼 개발 용어가 들어 있어도)
    - 금액, 날짜, 시각, 예시 숫자

## 답 반영

brief 문서는 답을 갖지 않는다.

- 마스터가 brief 를 보고 "A8. a" 처럼 답하면, `sdd:draft` 「답 반영」으로 `requirements.md` 를 고친 뒤 brief 를 다시 만든다
- 쉬운 말 점검에서 뜻이 정의되지 않은 말이 나오면 brief 에 정의를 더하지 않는다. 끝맺음에 "requirements.md 「도메인 언어」에 넣을 후보" 로 적는다
- brief 를 손으로 고치지 않는다. 다음에 다시 만들 때 사라진다
