# 기획 문서 (brief.md)

`sdd:brief` 가 쓰는 비개발자용 기획 문서의 모양이다. `references/spec-format.md` 에서 「한 번만 쓴다」「필요한 결정」「답 반영」만 따른다. 「마커」와 `references/draft.md` 의 EARS 는 개발 요소라서 따르지 않고, 대신 이 문서의 「결정 쓰는 법」「해야 할 일 쓰는 법」을 따른다.

## 담을 것과 뺄 것

- 담는다
    - 필요한 결정: 옵션, 예시, 추천안
    - 용어 뜻
    - 목적, 참여자, 정해진 원칙
    - 지금 이야기, 바뀐 뒤 이야기, 흐름 그림
    - 사용자 스토리, 확인 목록, 업무 규칙, 범위 밖
- 뺀다
    - 결정 표기(`@결정`·`@초안`·`@해석`·`@미정`·`@사실`·`@가정`·`@확정`)
    - EARS 문장(`WHEN …, THE System SHALL …`)
    - 코드 경로, 테이블, API, 코드 근거
    - 구현 위험, 별개로 나눌 개발 일

설명이나 조사 결과에 뺄 것이 섞여 있으면 문서에 쓰지 않는다. 끝맺음에 "요구사항이면 `sdd:draft`, 설계면 `sdd:design` 으로 넘길 것" 으로 한 줄씩 적는다.

## 쉬운 말

- 모든 문장을 일상에서 쓰는 말로 쓴다. 기술용어를 쓰지 않는다
- 업무 용어(예: 정산, 사원증 인증)가 꼭 필요하면 「쓰는 말」 절에 한 문장 뜻을 적고, 본문에서는 그 이름만 쓴다
- 금액·날짜·횟수는 실제 숫자로 쓴다. "일정 금액", "정해진 기간" 을 쓰지 않는다
- 쓸 때 참고하는 바꾸기 예시
    - "API 호출이 실패하면" → "화면에서 저장이 안 되면"
    - "레코드를 생성한다" → "목록에 한 줄이 새로 생긴다"
    - "배치로 정산한다" → "매달 1일에 한 번에 모아 계산한다"
    - "권한이 없으면" → "이 화면을 볼 수 없는 직원이면"

## 절 구성 (이 순서)

해당 없는 절은 지우지 말고 "해당 없음 — {이유 한 줄}" 로 남긴다. 요약·결론 절은 두지 않는다.

### 정해야 할 것

- 「열린 결정」과 「정해진 결정」 두 하위 절. 맨 위에 두는 이유는 마스터가 가장 먼저 할 일이기 때문이다
- 모양은 「결정 쓰는 법」을 따른다
- 결정이 모두 정해지면 「열린 결정」은 "없음" 한 줄이 된다

### 쓰는 말

- 용어마다 뜻 한 문장
- 마스터 정의는 원문 그대로 옮긴다. LLM 이 새로 붙인 이름은 "새로 붙인 이름" 이라고 밝힌다
- 용어끼리 부딪히는 곳은 어느 문장과 어느 문장이 다른지 인용만 하고 결정 ID 로 가리킨다

### 무엇을, 왜

- 목적 한 문장
- 참여자: 누가, 무엇을 하는지, 돈·물건·정보가 어떻게 오가는지
- 정해진 원칙: 마스터 문장을 불릿 하나씩

### 이야기

AS-IS 를 대신하는 절이다. 표나 단계 목록이 아니라 이야기로 쓴다.

- 지금 이야기: 기능이 생기기 전 인물이 겪는 일. 새 기능이면 "지금은 이렇게 한다" 를 쓴다
- 바뀐 뒤 이야기: 기능이 생긴 뒤 같은 인물이 같은 장면에서 겪는 일
- 이야기마다 이름 있는 인물 한 명, 장소 한 곳, 실제 숫자 하나 이상. 3~6문장. 인물 이름은 실제 직원 이름이 아니라 지어낸 이름
- 지금 1개 + 바뀐 뒤 1개가 기본이다. 인물 종류가 다르면(예: 고객, 점원) 인물마다 한 쌍
- 아직 정하지 않은 규칙이 이야기에 나오면 짐작으로 채우지 않고 결정 ID 를 가리킨다
- 흐름 그림은 이야기 뒤에 하나. 예시 숫자는 그림 한 곳에만 둔다

예시 (제휴카페):

```markdown
- 지금 이야기
    - 김민지 대리는 점심을 먹고 회사 1층 '빈카페'에서 아메리카노 한 잔을 산다. 값은 5,900원이다. 김 대리는 계산대에서 5,900원을 모두 낸다.
- 바뀐 뒤 이야기
    - 다음 날 김 대리는 같은 아메리카노를 고르고 계산대에서 사원증을 보여 준다. 점원이 화면에서 '제휴회사 직원' 버튼을 누르자 1,500원이 빠지고, 김 대리는 4,400원을 낸다. 라떼 두 잔을 한 번에 사면 몇 원이 빠지는지는 A6 에서 정한다.
```

### 해야 할 일

- 첫 문장: 해야 할 일의 개수와 각각 어디서 나왔는지 (마스터 문장, 빈 곳)
- 「해야 할 일 쓰는 법」대로 `### 해야 할 일 {n}: {이름}` 을 반복한다

## 결정 쓰는 법

spec-format 「필요한 결정」과 같다. 결정 표기만 쉬운 말로 바꾼다.

- 열린 결정
    - `**A1. {무엇을 정하는가}**` 한 문장
    - 예시: 옵션마다 결과가 어떻게 달라지는지 숫자로
    - 옵션 a/b/c 와 장단점 한 줄씩. 마스터가 "A1. a" 로 답할 수 있게 한다
    - `추천: a안 — {근거}`. LLM 이 알 수 없는 것(가격 정책, 계약 조건, 외부 합의)은 `추천 없음 — {이유 한 줄}`
    - `걸린 곳: 해야 할 일 2, 이야기`. 답을 반영할 자리를 이 목록으로 찾으므로 빠짐없이 적는다
- 정해진 결정
    - `**A1. {무엇을 정했는가}**` 한 문장
    - `답: {YYYY-MM-DD} "{답 원문}"`. 짧은 답을 풀어 썼으면 `풀어 쓴 뜻: …` 을 붙이고 끝맺음에서 맞는지 묻는다
    - `반영한 곳: …`. 반영한 규칙 내용은 다시 쓰지 않는다
    - 옵션, 예시, 추천 근거는 지운다

## 해야 할 일 쓰는 법

```markdown
### 해야 할 일 2: 메뉴 가격 바꾸기

**사용자 스토리:** 점주로서, 메뉴 가격을 바꿔서 원두값이 오른 만큼 반영하고 싶다.

**확인 목록**
1. 점주가 가격을 저장하면, 메뉴판에 바뀐 가격이 바로 보인다.
2. 가격이 0원 이하이면, 저장되지 않고 "가격은 1원 이상이어야 합니다" 가 보인다.
3. 메뉴가 '품절' 인 동안에는, 가격은 바꿀 수 있지만 주문은 받지 않는다.

**업무 규칙**
| 크기 | 가격 |
|---|---|
| 보통 | 기준 가격 |
| 큰 컵 | 기준 가격 + 500원 |

**범위 밖:** 지점마다 다른 가격 (다음 단계)
```

- 사용자 스토리: `{역할}로서, {행동}해서 {얻고 싶은 것}하고 싶다.` 역할은 점주·고객·운영 담당처럼 실제 사람이다
- 확인 목록: "~하면, ~된다" 한 문장에 조건 하나, 결과 하나. 결과가 둘이면 줄을 나눈다. 문장 끝에 아무 표기도 붙이지 않는다
- 업무 규칙: 값 대응, 계산식, 경계 예시처럼 문장으로 쓰면 길어지는 규칙. 경계는 양쪽 예시 행을 둔다 (예: 한도 1,500원 → 1,500원 할인됨, 1,501원 거부)
- 범위 밖: 다음 단계로 미룬 것, 비슷해 보이지만 하지 않는 것

- 흐름 그림은 ```mermaid `flowchart LR` 블록. 노드 라벨에 예시 숫자를 넣고, 그림 아래에 읽는 법 한두 문장. 그림 제목은 주제가 아니라 결론 문장이다
