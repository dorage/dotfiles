# sdd:draft — 구현 전 기획 초안 문서

설명 한 덩어리를 받아, 마스터가 결정만 내리면 구현에 들어갈 수 있는 기획 초안을 문서로 쓴다. 코드는 바꾸지 않는다.

먼저 `${CLAUDE_PLUGIN_ROOT}/references/spec-format.md` 와 `${CLAUDE_PLUGIN_ROOT}/references/draft.md` 를 읽는다. 결정·마커·답 반영은 앞 문서를, 절 구성과 요구사항 템플릿은 뒤 문서를 따른다. 이 스킬은 "문서를 어떤 순서로 쓰는가" 만 정한다.

- `sdd:quick`: 같은 포맷을 문서 없이 채팅 답으로 쓴다. 요구사항 1~2개, 결정 3개 이하인 작은 작업이면 그쪽을 권한다
- `spec-build`: 이미 있는 PR·브랜치를 검토하는 문서다. 이 스킬은 아직 코드가 없는 기능의 요구사항을 처음 세운다
- `sdd:design`: 이 문서를 입력으로 같은 폴더에 `design.md`(어떻게 만드는가)를 쓴다

## 형식 고르기

`{description}` 을 보고 하나를 고른다.

- "artifact", "아티팩트", "공유 문서", "Docs 로" 가 있다 → 「공유 문서 경로」
- 없다 → **기본값 「마크다운 경로」**

형식을 가리키는 말은 떼고, 나머지를 설명으로 쓴다.

## 설명 읽기

설명에서 아래를 뽑는다. 없는 것은 비워 두고 초안에서 채운다.

- 구현하려는 것: 기능 이름 하나 (예: 제휴카페). 문서 제목에 쓴다
- 도메인 언어: 마스터가 정의한 용어. 정의 문장을 그대로 옮기고 @결정 을 붙인다
- 목적과 정해진 원칙: 마스터 문장 하나에 @결정 하나
- 참여자: 마스터가 나열한 참여 주체(예: 키오스크 고객, 앱 고객, 카페 사장님, 관리자, 제휴회사, 임직원). 빠짐없이 「참여자」 표에 옮기고 @결정 을 붙인다
- 템플릿: 마스터가 준 요구사항 템플릿 (우선순위는 `references/draft.md` 「요구사항 템플릿」)
- 저장 경로: 경로처럼 보이는 문자열(`docs/…`, `*.md`)

설명이 비어 있으면(무엇을 만들지 없음) 쓰지 말고 무엇의 기획 초안인지 한 번 묻는다.

## 마크다운 경로

### 저장 경로 정하기

spec-format 「저장 위치」를 따른다. 파일 이름은 `requirements.md` 다.

- 마스터가 요청하기 전에는 이 파일을 커밋하지 않는다

### 쓰는 순서

- **뼈대 먼저.** Write 로 `references/draft.md` 「절 구성」의 제목과 기준 줄, `## 절` 헤딩, 절마다 `(작성 중)` 한 줄을 만든다
- 「조사」를 한다
- Edit 로 절 하나씩 채운다. 절 하나를 채울 때마다 채팅에 "지금 {절} 작성 중" 한 줄을 남긴다
- 「필요한 결정」은 마지막에 채운다. 다른 절을 쓰면서 드러난 빈 곳이 모여야 쓸 수 있다
- 다 쓰면 `(작성 중)` 이 남았는지 검색해 없앤다
- 「참여자별 검토」를 한다
- spec-format 「윤문」을 거친다

## 참여자별 검토

참여자마다 그 사람 입장에서 빠진 과정을 찾는 일은 `sdd:persona-review` 가 맡는다. 참여자가 확정되어야 검토가 헛일이 되지 않는다.

- 「참여자」 표의 참여자가 모두 @결정 이면: `Skill(skill="sdd:persona-review", args="{requirements.md 경로}")` 를 부른다. persona-review 가 같은 문서에 빈 곳과 「참여자별 검토 기록」을 더한다
- 참여자에 @초안 이 하나라도 있으면: 부르지 않는다. 「필요한 결정」에 "참여자가 이 목록이 맞는가" 결정을 올린다. 옵션은 a) 이 목록 그대로 / b) 더하거나 뺄 참여자를 답에 적기. 답이 오면 「답 반영」에서 부른다
- 공유 문서 경로에서는 부르지 않는다. persona-review 는 로컬 마크다운만 고친다. 끝맺음에 "참여자별 검토는 로컬 문서에서 `/sdd:persona-review` 로 돌리세요" 한 줄을 적는다
- persona-review 가 돌려준 새 결정 ID 와 더한 인수 조건 자리는 끝맺음의 "무엇을 썼는지" 불릿에 합친다

## 공유 문서 경로

`spec-build-artifact` 의 「도구 확인」「Docs 경로」「대체 경로」를 그대로 따른다. 다른 점만 적는다.

- 뼈대의 `pending` 블록은 `references/draft.md` 「절 구성」의 절마다 하나다. `intent` 에 절 이름과 들어갈 내용을 적는다
- 흐름 그림은 widget 다이어그램으로 그리고 screenshot 으로 확인한다
- 다 채우면 문서 링크를 프로젝트 메모리에 `reference` 로 남긴다. 다음 세션이 같은 문서를 찾게 하기 위해서다. 결정 내용은 메모리에 옮기지 않는다. 문서와 메모리가 어긋나기 때문이다

## 조사

초안의 목적은 결정을 끌어내는 것이다. 조사는 결정과 요구사항에 필요한 만큼만 한다.

- `git fetch` 후 `origin/main` 기준으로 읽는다 (`git grep … origin/main`, `git show origin/main:{path}`)
- 설명의 용어·개념과 닮은 기존 기능을 찾는다: 테이블·마이그레이션, 서비스, 정산·결제 주기, wiki 스펙
- 찾은 것은 문서의 「기존 시스템과 맞닿는 곳」에 `@사실 ({경로})` 로 적고, 요구사항과 결정의 근거로 쓴다
- 확인하지 못한 것은 "확인하지 않았다" 로 적는다. 짐작을 @사실 로 쓰지 않는다
- 마스터 문장끼리 부딪히는 곳을 찾는다. 같은 용어가 문장마다 다른 뜻이면 결정 항목으로 올린다

## 답 반영

spec-format 「답 반영」대로 같은 문서를 고친다. 새 문서를 만들지 않는다. 고친 뒤 spec-format 「윤문」을 다시 거친다.

- 참여자 목록 결정에 답이 와서 참여자가 모두 @확정 또는 @결정 이 되면, 윤문 전에 「참여자별 검토」대로 `sdd:persona-review` 를 부른다
- 이미 「참여자별 검토 기록」이 있는 문서에 참여자를 더했으면, persona-review 가 더한 참여자만 검토한다

## 끝맺음

- 첫 줄
    - 열린 결정이 있으면: 다음에 답할 결정 하나. 구체 예시와 추천안을 붙인다 (예: "A6 에 답해 주세요. 한도 1,500원에 라떼 2잔을 한 줄로 주문하면, 잔마다 세면 3,000원, 줄마다 세면 1,500원이 할인됩니다. 추천은 잔마다입니다.")
    - 열린 결정이 없으면: 설계 문서를 쓰는 다음 명령 한 줄 (예: `/sdd:design ~/.sdd/dotfiles/20261102143005_제휴카페-임직원-할인/requirements.md`)
- 둘째 줄: 문서 경로(클릭 가능한 `path`) 또는 문서 링크
- 무엇을 썼는지·바꿨는지 불릿 5개 이하. 문서 내용을 채팅에 다시 늘어놓지 않는다
- 원문에 없던 새 발견이나 구현 전 확인할 위험은 3개 이하, 한 줄씩

## 하지 않는 것

- 코드를 바꾸지 않는다
- 경로를 정하기 전에 마크다운 파일을 쓰지 않는다
- 공유 문서 경로에서 조사를 다 마친 뒤 문서를 한 번에 만들지 않는다. 뼈대가 조사보다 먼저다
- 마스터가 정한 용어 정의를 다듬어 바꾸지 않는다. 문제가 있으면 결정 항목으로 올린다
