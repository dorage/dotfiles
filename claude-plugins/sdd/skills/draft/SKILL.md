# sdd:draft — 구현 전 기획 초안 문서

설명 한 덩어리를 받아, 마스터가 결정만 내리면 구현에 들어갈 수 있는 기획 초안을 문서로 쓴다. 코드는 바꾸지 않는다.

먼저 `${CLAUDE_PLUGIN_ROOT}/references/spec-format.md` 를 읽는다. 결정·요구사항·마커·답 반영의 모양은 전부 그 문서를 따른다. 이 스킬은 "문서를 어디에 어떤 절로 쓰는가" 만 정한다.

- `sdd:quick`: 같은 포맷을 문서 없이 채팅 답으로 쓴다. 요구사항 1~2개, 결정 3개 이하인 작은 작업이면 그쪽을 권한다
- `spec-build`: 이미 있는 PR·브랜치를 검토하는 문서다. 이 스킬은 아직 코드가 없는 기능의 요구사항을 처음 세운다
- `sdd:design`: 이 문서를 입력으로 같은 폴더에 `design.md`(어떻게 만드는가)를 쓴다

## 형식 고르기

`{description}` 을 보고 하나를 고른다.

- "artifact", "아티팩트", "공유 문서", "Docs 로" 가 있다 → 「공유 문서 경로」
- 없다 → **기본값 「마크다운 경로」**

형식을 가리키는 말은 떼고, 나머지를 설명으로 쓴다.

## 설명 읽기

설명에서 아래를 뽑는다. 없는 것은 비워 두고 초안에서 채운다.

- 구현하려는 것: 기능 이름 하나 (예: 제휴카페). 문서 제목은 `{기능} 기획 초안`
- 도메인 언어: 마스터가 정의한 용어. 정의 문장을 그대로 옮기고 @결정 을 붙인다
- 목적과 정해진 원칙: 마스터 문장 하나에 @결정 하나
- 템플릿: 마스터가 요구사항 템플릿을 주면 포맷 문서의 템플릿보다 우선한다
- 저장 경로: 경로처럼 보이는 문자열(`docs/…`, `*.md`)

설명이 비어 있으면(무엇을 만들지 없음) 쓰지 말고 무엇의 기획 초안인지 한 번 묻는다.

## 마크다운 경로

### 저장 경로 정하기

요구사항 문서는 기능마다 폴더 하나에 `requirements.md` 로 둔다. 같은 폴더에 `sdd:design` 의 `design.md`, `sdd:brief` 의 `brief.md` 가 모인다. 경로가 정해지기 전에는 파일을 쓰지 않는다.

- 설명에 경로가 있다 → 그 경로. 폴더면 그 안의 `requirements.md`
- 없으면 현재 리포의 `origin/main` 에서 같은 기능의 폴더를 찾는다: `git ls-tree -r --name-only origin/main | grep -E '(^|/)(requirements|design|brief)\.md$'`
    - 기능 이름과 맞는 폴더가 정확히 하나다 → 그 폴더. 쓰기 전에 채팅에 "{경로}에 씁니다" 한 줄을 남긴다
    - 없다 → 기본값 `.claude/specs/{slug}/requirements.md`. 쓰기 전에 같은 한 줄을 남긴다
    - 둘 이상이다 → `AskUserQuestion` 한 번으로 묻는다. 찾은 후보와 기본값을 옵션으로 주고, 추천안을 첫 옵션에 둔다
- `slug` 는 기능 이름의 영어 kebab-case 50자 이내 (예: `partner-cafe`)
- 같은 파일이 이미 있으면 덮어쓰기 전에 읽고, 갱신인지 새 파일인지 한 번 묻는다
- 마스터가 요청하기 전에는 이 파일을 커밋하지 않는다

### 쓰는 순서

- **뼈대 먼저.** Write 로 제목, 기준 날짜, 「절 구성」의 `## 절` 헤딩, 절마다 `(작성 중)` 한 줄을 만든다
- 「조사」를 한다
- Edit 로 절 하나씩 채운다. 절 하나를 채울 때마다 채팅에 "지금 {절} 작성 중" 한 줄을 남긴다
- 「필요한 결정」은 마지막에 채운다. 다른 절을 쓰면서 드러난 빈 곳이 모여야 쓸 수 있다
- 다 쓰면 `(작성 중)` 이 남았는지 검색해 없앤다

### 마크다운 형식

- 표와 숫자 목록은 포맷 문서의 「요구사항 템플릿」이 정한 자리에만 쓴다. 「도메인 언어」를 포함한 나머지는 2단 불릿
- 흐름 그림은 ```mermaid `flowchart LR` 블록. 노드 라벨에 예시 숫자를 넣고, 그림 아래에 읽는 법 한두 문장

## 공유 문서 경로

`spec-build-artifact` 의 「도구 확인」「Docs 경로」「대체 경로」를 그대로 따른다. 다른 점만 적는다.

- 뼈대의 `pending` 블록은 「절 구성」의 절마다 하나다. `intent` 에 절 이름과 들어갈 내용을 적는다
- 흐름 그림은 widget 다이어그램으로 그리고 screenshot 으로 확인한다
- 표는 어디든 써도 된다. 문서 화면이 표를 그려 주기 때문이다
- 다 채우면 문서 링크를 프로젝트 메모리에 `reference` 로 남긴다. 다음 세션이 같은 문서를 찾게 하기 위해서다. 결정 내용은 메모리에 옮기지 않는다. 문서와 메모리가 어긋나기 때문이다

## 조사

초안의 목적은 결정을 끌어내는 것이다. 조사는 결정과 요구사항에 필요한 만큼만 한다.

- `git fetch` 후 `origin/main` 기준으로 읽는다 (`git grep … origin/main`, `git show origin/main:{path}`)
- 설명의 용어·개념과 닮은 기존 기능을 찾는다: 테이블·마이그레이션, 서비스, 정산·결제 주기, wiki 스펙
- 찾은 것은 「기존 시스템과 맞닿는 곳」에 `@사실 ({경로})` 로 적고, 요구사항과 결정의 근거로 쓴다
- 확인하지 못한 것은 "확인하지 않았다" 로 적는다. 짐작을 @사실 로 쓰지 않는다
- 마스터 문장끼리 부딪히는 곳을 찾는다. 같은 용어가 문장마다 다른 뜻이면 결정 항목으로 올린다

## 절 구성 (이 순서)

해당 없는 절은 지우지 말고 "해당 없음 — {이유 한 줄}" 로 남긴다. 요약·결론 절은 두지 않는다 (포맷 문서 「한 번만 쓴다」).

### 필요한 결정

- 포맷 문서의 「필요한 결정」 모양대로 「열린 결정」과 「정해진 결정」 두 하위 절
- 맨 위에 두는 이유는 마스터가 가장 먼저 할 일이기 때문이다. 결정이 모두 정해지면 「열린 결정」은 "없음" 한 줄이 된다

### 도메인 언어

- 용어마다 뜻과 표기. 마스터 정의는 고치지 않고 @결정 (공유 문서면 표, 마크다운이면 2단 불릿)
- LLM 이 새로 붙인 이름은 @초안 으로 따로 적는다
- 용어끼리 부딪히는 곳은 어느 문장과 어느 문장이 다른지 인용만 하고 결정 ID 로 가리킨다. 선택지는 「필요한 결정」에만 쓴다

### {기능}이란

- 목적 한 문장
- 참여자: 누가, 무엇을 하는지, 돈·데이터가 어떻게 오가는지
- 정해진 원칙: 마스터 문장을 불릿 하나씩, 모두 @결정
- 비슷한 기존 기능이 있으면 차이를 적는다

### 핵심 흐름

- 구체 예시 1건으로 처음부터 끝까지 보인다 (예: 정가 5,900원 아메리카노 1잔 주문 → 누가 언제 얼마를 받는지)
- 금액·날짜·수치는 실제 숫자로 쓴다. "일정 금액" 같은 말을 쓰지 않는다
- 그림 제목은 주제가 아니라 결론 문장이다

### 요구사항

- 첫 문장: 요구사항 개수와 각각 어디서 나왔는지 (마스터 문장, 외부 요청 등)
- 포맷 문서의 「요구사항 템플릿」대로 `### 요구사항 {n}: {이름}` 을 반복한다

### 기존 시스템과 맞닿는 곳

- 코드에서 확인한 사실: `@사실 ({경로})` 와 이 기능에 주는 뜻
- 구현 전에 확인해야 할 위험 (예: 기존 정산이 새 할인분까지 지급하는가)
- 별개 작업으로 나눌 것. 요구사항 하나에만 걸린 범위 밖은 그 요구사항의 「범위 밖」에만 쓴다

## 답 반영

포맷 문서의 「답 반영」대로 같은 문서를 고친다. 새 문서를 만들지 않는다.

## 끝맺음

- 첫 줄
    - 열린 결정이 있으면: 다음에 답할 결정 하나. 구체 예시와 추천안을 붙인다 (예: "A6 에 답해 주세요. 한도 1,500원에 라떼 2잔을 한 줄로 주문하면, 잔마다 세면 3,000원, 줄마다 세면 1,500원이 할인됩니다. 추천은 잔마다입니다.")
    - 열린 결정이 없으면: 설계 문서를 쓰는 다음 명령 한 줄 (예: `/sdd:design .claude/specs/partner-cafe/requirements.md`)
- 둘째 줄: 문서 경로(클릭 가능한 `path`) 또는 문서 링크
- 무엇을 썼는지·바꿨는지 불릿 5개 이하. 문서 내용을 채팅에 다시 늘어놓지 않는다
- 원문에 없던 새 발견이나 구현 전 확인할 위험은 3개 이하, 한 줄씩

## 하지 않는 것

- 코드를 바꾸지 않는다
- 경로를 정하기 전에 마크다운 파일을 쓰지 않는다
- 공유 문서 경로에서 조사를 다 마친 뒤 문서를 한 번에 만들지 않는다. 뼈대가 조사보다 먼저다
- 마스터가 정한 용어 정의를 다듬어 바꾸지 않는다. 문제가 있으면 결정 항목으로 올린다
