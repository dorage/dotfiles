# sdd:design — 요구사항 다음의 설계 문서

요구사항 문서를 받아 "어떻게 만드는가" 를 설계 문서로 쓴다. 구현자가 코드 위치와 순서를 고르기만 하면 되게 하는 것이 목적이다. 코드는 바꾸지 않는다.

먼저 `${CLAUDE_PLUGIN_ROOT}/references/spec-format.md` 를 읽는다. 「한 번만 쓴다」「필요한 결정」「마커」「답 반영」은 그 문서를 따른다. 이 스킬은 설계 문서의 절 구성과, 포맷 문서에 없는 결정 표기(볼드·이탤릭·`->`)만 정한다.

- `sdd:draft`: 같은 기능의 요구사항 문서(무엇을). 이 스킬의 입력이다
- `sdd:brief`: 같은 기능의 비개발자용 기획 문서
- `sdd:quick`: 요구사항 문서 없이 작은 작업의 스펙과 설계를 채팅 답 하나로 쓴다. 요구사항 문서가 이미 있으면 작아도 이 스킬로 짧은 `design.md` 를 쓴다
- `spec-build`: 이미 있는 PR·브랜치를 검토한다. 이 스킬은 코드가 없을 때 쓴다
- `spec-bdd`: Gherkin 시나리오를 쓴다. 이 스킬의 테스트 전략은 시나리오를 다시 쓰지 않는다

## 입력 찾기

- 포맷 문서 「저장 위치」의 「폴더 고르기」로 폴더를 정하고, 그 안의 `requirements.md` 를 입력으로 쓴다. 고른 폴더에 `requirements.md` 가 없으면 쓰지 않고 "`/sdd:draft` 를 먼저 실행하세요" 한 줄을 남긴다
- 요구사항 문서를 끝까지 읽는다. 앞부분만 보고 쓰지 않는다
- 요구사항 문서에 `(작성 중)` 이 남아 있으면 쓰지 않고, 그 절 이름을 알려 준다
- 요구사항 문서의 「열린 결정」이 남아 있어도 **멈추지 않는다.** 마스터가 설계를 보고 그 결정의 트레이드오프를 비교하려는 것일 수 있다. 쓰는 법은 「요구사항의 열린 결정」을 따른다

## 저장 위치

- 요구사항 문서와 같은 폴더의 `design.md`. 나머지는 포맷 문서의 「저장 위치」를 따른다
- 마스터가 요청하기 전에는 커밋하지 않는다

## 쓰는 순서

- **뼈대 먼저.** Write 로 제목(`{기능} 설계`), 기준 날짜, 기준 코드(`origin/main` 커밋), 입력 요구사항 문서 경로, 「절 구성」의 `## 절` 헤딩, 절마다 `(작성 중)` 한 줄을 만든다
- 「조사」를 한다
- Edit 로 절 하나씩 채운다. 절 하나를 채울 때마다 채팅에 "지금 {절} 작성 중" 한 줄을 남긴다
- 「요구사항 추적」을 채우며 빠진 인수 조건을 센다. 빠진 줄이 있으면 그 절로 돌아간다
- 「필요한 결정」은 마지막에 채운다
- `(작성 중)` 이 남았는지 검색해 없앤다

## 조사

- `git fetch` 후 `origin/main` 기준으로 읽는다 (`git grep … origin/main`, `git show origin/main:{path}`)
- 요구사항 문서의 「기존 시스템과 맞닿는 곳」에서 시작해, 바꿀 자리의 진입점·도메인 규칙·스키마·테스트 구조를 직접 읽는다
- 기존 컴포넌트는 `@사실 ({origin/main 경로})` 로 적는다. 확인하지 못한 것은 "확인하지 않았다" 로 적는다
- 테스트 도구와 테스트 위치(단위·통합·E2E 가 어디 있는지)를 확인한다. 「테스트 전략」의 층을 고르는 근거다

## 한 번만 쓴다 (두 문서 사이)

- 요구사항 문서의 규칙·수치·용어를 다시 쓰지 않는다. `요구사항 {n} 인수 조건 {m}`, `요구사항 {n} 업무 규칙`, 용어 이름으로 가리킨다
- 설계 중 드러난 **사용자에게 보이는 새 동작**은 설계 문서에 규칙으로 쓰지 않는다. 요구사항 문서의 열린 결정으로 올릴 문장을 끝맺음에 제안한다 (역반영). 예: 결제 대행사 응답이 10초를 넘을 때 고객 화면 문구
- 사용자에게 보이지 않는 동작(내부 재시도, 로그)은 설계 문서 안에서 정하고 `@초안` 을 단다

## 요구사항의 열린 결정

요구사항 문서에 열린 결정이 남아 있으면 그 결정에 걸린 설계를 이렇게 쓴다.

- 설계 본문은 그 결정의 추천안 기준으로 쓰고, 그 자리 마커는 `@가정 ({결정 ID} 추천안)` 이다
- 바로 아래에 다른 옵션이면 바뀌는 자리를 차이 목록으로 붙인다

```markdown
- `PartnerDiscountCalculator.calc(cup: Cup): Won` — 잔마다 계산 @가정 (A3 추천안)
    - A3 이 b(줄마다) 이면: 인터페이스가 `calc(line: OrderLine): Won` 이 되고, 「시퀀스 다이어그램」 호출이 2번 → 1번으로 준다
```

- 요구사항 문서의 `@미정` 에 걸린 설계는 쓰지 않고 "@미정 대기 (요구사항 {n})" 로 남긴다

## 결정 표기

포맷 문서의 「필요한 결정」 모양에 아래를 더한다.

- 그룹 문자는 `D` 부터 쓴다. 요구사항 문서의 `A`~`C` 와 겹치지 않게 하기 위해서다. 그룹마다 5개 이하
- 결정 제목 끝에 `->` 를 둔다. 마스터가 그 옆에 답을 적는 자리다
- **볼드 제목**: 마스터가 정해야 하는 결정. 되돌리기 어려운 선택이 여기에 온다
- *이탤릭 제목*: 추천안을 설계 본문에 이미 적용한 결정. 마스터가 원할 때 `->` 옆에 다른 옵션을 적어 바꾼다
- 볼드와 이탤릭은 같은 그룹 안에 섞여 놓인다. 따로 절을 만들지 않는다

```markdown
#### D 저장

- **D1. 제휴 할인액을 주문 테이블 컬럼으로 둘지, 별도 테이블로 둘지** ->
    - 예시: 라떼 2잔 주문 1건 → a안은 `orders` 1행에 3,000원, b안은 `order_discounts` 2행에 1,500원씩
    - a. … — …
    - b. … — …
    - 추천: @초안 a안 — …
    - 걸린 곳: 컴포넌트 설계 `OrderRepository`, 데이터 흐름
- *D2. 할인 계산을 서비스 함수로 둔다* ->
    - 적용한 안: a. 서비스 함수 — 테스트가 쉽다
    - 대안: b. 클래스 — 상태가 필요해지면 바꾼다
    - 걸린 곳: 컴포넌트 설계 `PartnerDiscountCalculator`
```

### 되돌리기 판정

- 어려움 → 볼드: 바꾸려면 운영 데이터나 바깥 사용자까지 고쳐야 한다
    - 예: 테이블·컬럼 추가, 결제 대행사 같은 외부 연동, 공개 API 모양
- 쉬움 → 이탤릭: 코드나 설정만 바꾸면 된다
    - 예: 함수로 둘지 클래스로 둘지, 캐시를 쓸지

## 절 구성 (이 순서)

해당 없는 절은 지우지 말고 "해당 없음 — {이유 한 줄}" 로 남긴다. 요약·결론 절은 두지 않는다.

표는 「컴포넌트 설계」「오류 처리」「요구사항 추적」 세 절에서만 쓴다. 비교가 한눈에 보여야 하는 자리라서 마스터가 마크다운 규칙(표 금지)의 예외로 정했다. 나머지 절은 2단 불릿이다.

### 필요한 결정

- 「열린 결정」과 「정해진 결정」 두 하위 절. 모양은 「결정 표기」
- 열린 결정에는 볼드(답이 필요)와 이탤릭(추천안 적용)이 함께 놓인다
- 볼드 결정이 모두 정해지면 「열린 결정」에는 이탤릭만 남는다. 이탤릭도 없으면 "없음" 한 줄

### 시스템 아키텍처

- 첫 문장: 새 기능이 기존 시스템 어디에 붙는지 한 문장
- ```mermaid `flowchart LR` 하나. 새 컴포넌트와 기존 컴포넌트를 `classDef new` / `classDef existing` 처럼 다른 클래스로 구분한다
- 노드 라벨은 한 줄 20자 안팎, 줄바꿈은 `<br/>`. 참여 상자가 6개를 넘으면 묶는다
- 그림 아래에 읽는 법 한두 문장. 기존 컴포넌트의 `@사실` 경로는 「컴포넌트 설계」 표에만 둔다

### 컴포넌트 설계

표 한 개. 열은 컴포넌트, 책임, 인터페이스, 의존, 추적, 표기.

```markdown
| 컴포넌트 | 책임 | 인터페이스 | 의존 | 추적 | 표기 |
|---|---|---|---|---|---|
| `PartnerDiscountCalculator` (새) | 주문 한 잔의 제휴 할인액을 계산한다 | `calc(cup: Cup): Won` | `PartnerRepository` | 요구사항 2 인수 조건 1~3 | @가정 (A3 추천안) |
| `SettlementJob` (기존) | 월 정산을 만든다 | 변경 없음 | — | 요구사항 4 인수 조건 2 | @사실 (`src/settlement/job.ts`) |
```

- 책임은 한 문장. 둘이면 컴포넌트를 나눈다
- 인터페이스는 함수 시그니처, API 메서드·경로, 이벤트 이름 중 바깥에서 보이는 것
- 컴포넌트마다 대안이 있으면 「필요한 결정」에 볼드 또는 이탤릭 결정으로 올리고, 표기 칸에서 결정 ID 를 가리킨다
- 요구사항 문서의 열린 결정에 걸리면 표 아래에 차이 목록을 붙인다 (「요구사항의 열린 결정」)

### 시퀀스 다이어그램

- 요구사항 문서 「핵심 흐름」의 예시를 그대로 시나리오로 쓴다. 새 예시를 지어내지 않는다
- ```mermaid `sequenceDiagram`. 그림 하나에 성공 경로 하나. 실패는 「오류 처리」의 오류 ID 로 가리킨다
- 메시지 라벨에 예시 숫자를 넣는다 (예: `calc(5,900원) → 1,500원`)
- 그림 개수는 요구사항 개수 이하. 넘으면 요구사항 2개를 한 그림으로 묶는다
- 그림 제목은 주제가 아니라 결론 문장이다. 그림 아래에 읽는 법 한두 문장

### 데이터 흐름

- 데이터마다 2단 불릿: 생성 위치, 저장소(테이블·큐·캐시·파일), 읽는 컴포넌트, 보존 기간
- 테이블이나 컬럼이 바뀌면 ```mermaid `erDiagram` 으로 **바뀌는 테이블만** 그린다. 컬럼 타입과 소수점 자릿수를 적는다
- 금액·정산 컬럼은 포맷 문서 「명세화」대로 소수점 정확도를 확인한다. 요구사항 문서에 답이 없으면 열린 결정으로 올린다

### 오류 처리

표 한 개. 열은 ID, 발생 자리, 감지, 사용자에게 보이는 것, 복구, 실패 방향, 추적, 표기.

```markdown
| ID | 발생 자리 | 감지 | 사용자에게 보이는 것 | 복구 | 실패 방향 | 추적 | 표기 |
|---|---|---|---|---|---|---|---|
| E1 | `SettlementJob` DB 잠금 | 쿼리 타임아웃 5초 | 없음 | 1분 간격 3회 재시도, 실패 시 알람 | 시끄러움 | 요구사항 4 인수 조건 3 | @초안 |
```

- 실패 방향은 넷 중 하나: 덜 줌, 두 번 줌, 조용함, 시끄러움
- 요구사항 문서의 `IF …, THEN` 인수 조건마다 오류 행이 하나 이상 있어야 한다
- 돈·정산이 걸린 오류는 복구 칸에 멱등 키와 중복 지급을 막는 장치를 적는다
- 사용자에게 보이는데 요구사항 문서에 없는 오류는 행을 만들지 않는다. 역반영으로 돌린다 (「한 번만 쓴다」)

### 테스트 전략

- 인수 조건의 행동을 다시 쓰지 않는다. 층과 경계만 정한다. 시나리오는 구현 때 `spec-bdd` 가 쓴다
- 층 고르는 기준 (2단 불릿으로 쓴다)
    - 단위: 계산식·값 대응(업무 규칙 표)
    - 통합: 컴포넌트 2개 이상 + 저장소
    - E2E: 사용자 화면에서 끝나는 흐름
    - 운영 확인: 외부 계약·운영 데이터에 기대는 것. 확인 쿼리·명령과 통과 기준을 적는다
- 테스트 더블(가짜 결제 대행사, 고정 시계)을 쓰는 경계를 컴포넌트 이름으로 적는다
- 요구사항 문서 업무 규칙의 경계 행(예: 1,500원 할인됨, 1,501원 거부)을 경계 테스트 대상으로 가리킨다
- 자동 테스트로 지킬 수 없는 인수 조건은 이유와 운영 확인 방법을 적는다
- 층 배정 자체는 「요구사항 추적」 표의 테스트 칸에 쓴다. 이 절에서 인수 조건별로 다시 나열하지 않는다

### 요구사항 추적

표 한 개. 요구사항 문서의 인수 조건마다 한 행. 열은 인수 조건, 컴포넌트, 시퀀스, 오류, 테스트 층.

```markdown
| 인수 조건 | 컴포넌트 | 시퀀스 | 오류 | 테스트 층 |
|---|---|---|---|---|
| 요구사항 2 인수 조건 1 | `PartnerDiscountCalculator` | 주문 시퀀스 | — | 단위 |
| 요구사항 2 인수 조건 2 | `OrderController` | — | E2 | 통합 |
```

- 첫 문장: "인수 조건 {N}개 중 {N}개를 가리킨다" 와 기준 날짜
- 어떤 설계 요소도 가리키지 않는 인수 조건은 그 절로 돌아가 채운다. 설계가 필요 없으면 컴포넌트 칸에 "설계 없음 — {이유}"
- 이 표가 꽉 차기 전에는 끝맺지 않는다

## 답 반영

포맷 문서의 「답 반영」대로 같은 설계 문서를 고친다. 새 문서를 만들지 않는다. 다른 점만 적는다.

- 답은 두 군데서 온다: 채팅의 "D1. a", 문서의 결정 제목 `->` 옆. 둘 다 읽는다
- `->` 옆 답이 "추천안" 이면 추천안을 `@확정` 으로 옮긴다
- `->` 옆이 비어 있는 볼드 결정은 「열린 결정」에 그대로 두고 끝맺음 첫 줄에서 다시 묻는다
- 이탤릭 결정에 다른 옵션이 적히면, 그 결정의 「걸린 곳」을 모두 고치고 「정해진 결정」으로 옮긴다
- 요구사항 문서가 바뀌면(답 반영, 요구사항 추가) 「요구사항 추적」에서 바뀐 번호를 찾아 걸린 설계만 고친다. `@가정 ({ID} 추천안)` 자리는 답에 맞게 고치고 차이 목록을 지운다

## 완성

두 문서 모두 아래가 맞으면 완성이다. 완성은 다음 단계(구현 계획)로 넘어가는 조건이며, 설계 문서를 쓰는 조건이 아니다.

- 「열린 결정」에 볼드 결정이 0개다. 이탤릭 결정은 남아 있어도 된다
- `@미정` 이 0개다
- 「요구사항 추적」 표가 꽉 차 있다

## 끝맺음

- 첫 줄
    - 완성이면: "완성 — 다음 단계로 넘어갈 수 있습니다." 와 다음 명령 한 줄 (예: `/sdd:task ~/.sdd/dotfiles/20261102143005_제휴카페-임직원-할인/`)
    - 아니면: 다음에 답할 결정 하나. 요구사항 문서의 열린 결정이 먼저다. 구체 예시와 추천안을 붙인다
- 둘째 줄: 문서 경로(클릭 가능한 `path`)
- 무엇을 썼는지·바꿨는지 불릿 5개 이하. 「요구사항 추적」 숫자(예: 18/18)를 포함한다. 문서 내용을 다시 늘어놓지 않는다
- 역반영 제안이 있으면 요구사항 문서에 올릴 결정 문장을 한 줄씩, 3개 이하
- 구현 전에 확인할 위험은 3개 이하, 한 줄씩

## 하지 않는 것

- 코드를 바꾸지 않는다
- 요구사항 문서를 고치지 않는다. 역반영은 제안만 하고, 반영은 `sdd:draft` 의 「답 반영」이 한다
- 요구사항 문서의 규칙·수치를 설계 문서에 옮겨 적지 않는다
- 요구사항 문서의 열린 결정을 이유로 멈추지 않는다
- 인수 조건을 Gherkin 이나 테스트 문장으로 다시 쓰지 않는다
