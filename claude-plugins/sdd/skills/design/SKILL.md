# sdd:design — 요구사항 다음의 설계 문서

요구사항 문서를 받아 "어떻게 만드는가" 를 설계 문서로 쓴다. 구현자가 코드 위치와 순서를 고르기만 하면 되게 하는 것이 목적이다. 코드는 바꾸지 않는다.

먼저 `${CLAUDE_PLUGIN_ROOT}/references/spec-format.md` 와 `${CLAUDE_PLUGIN_ROOT}/references/design.md` 를 읽는다. 결정·마커·답 반영은 앞 문서를, 절 구성·결정 표기·완성 조건은 뒤 문서를 따른다. 이 스킬은 "문서를 어떤 순서로 쓰는가" 만 정한다.

- `sdd:draft`: 같은 기능의 요구사항 문서(무엇을). 이 스킬의 입력이다
- `sdd:brief-dev`·`sdd:brief-nondev`: 같은 요구사항 문서를 마커 없이 옮긴 개발자용·비개발자용 기획 문서
- `sdd:quick`: 요구사항 문서 없이 작은 작업의 스펙과 설계를 채팅 답 하나로 쓴다. 요구사항 문서가 이미 있으면 작아도 이 스킬로 짧은 `design.md` 를 쓴다
- `spec-build`: 이미 있는 PR·브랜치를 검토한다. 이 스킬은 코드가 없을 때 쓴다
- `sdd:bdd`: Gherkin 시나리오를 쓴다. 이 스킬의 테스트 전략은 시나리오를 다시 쓰지 않는다

## 입력 찾기

- spec-format 「저장 위치」의 「폴더 고르기」로 폴더를 정하고, 그 안의 `requirements.md` 를 입력으로 쓴다. 고른 폴더에 `requirements.md` 가 없으면 쓰지 않고 "`/sdd:draft` 를 먼저 실행하세요" 한 줄을 남긴다
- 요구사항 문서를 끝까지 읽는다. 앞부분만 보고 쓰지 않는다
- 요구사항 문서에 `(작성 중)` 이 남아 있으면 쓰지 않고, 그 절 이름을 알려 준다
- 요구사항 문서의 「열린 결정」이 남아 있어도 **멈추지 않는다.** 마스터가 설계를 보고 그 결정의 트레이드오프를 비교하려는 것일 수 있다. 쓰는 법은 `references/design.md` 「요구사항의 열린 결정」을 따른다

## 저장 위치

- 요구사항 문서와 같은 폴더의 `design.md`. 나머지는 spec-format 「저장 위치」를 따른다
- 마스터가 요청하기 전에는 커밋하지 않는다

## 쓰는 순서

- **뼈대 먼저.** Write 로 제목(`{기능} 설계`), 기준 날짜, 기준 코드(`origin/main` 커밋), 입력 요구사항 문서 경로, `references/design.md` 「절 구성」의 `## 절` 헤딩, 절마다 `(작성 중)` 한 줄을 만든다
- 「조사」를 한다
- Edit 로 절 하나씩 채운다. 절 하나를 채울 때마다 채팅에 "지금 {절} 작성 중" 한 줄을 남긴다
- 「요구사항 추적」을 채우며 빠진 인수 조건을 센다. 빠진 줄이 있으면 그 절로 돌아간다
- 「필요한 결정」은 마지막에 채운다
- `(작성 중)` 이 남았는지 검색해 없앤다
- spec-format 「윤문」을 거친다

## 조사

- `git fetch` 후 `origin/main` 기준으로 읽는다 (`git grep … origin/main`, `git show origin/main:{path}`)
- 요구사항 문서의 「기존 시스템과 맞닿는 곳」에서 시작해, 바꿀 자리의 진입점·도메인 규칙·스키마·테스트 구조를 직접 읽는다
- 기존 컴포넌트는 `@사실 ({origin/main 경로})` 로 적는다. 확인하지 못한 것은 "확인하지 않았다" 로 적는다
- 테스트 도구와 테스트 위치(단위·통합·E2E 가 어디 있는지)를 확인한다. 문서 「테스트 전략」의 층을 고르는 근거다

## 답 반영

spec-format 「답 반영」대로 같은 설계 문서를 고친다. 새 문서를 만들지 않는다. 고친 뒤 spec-format 「윤문」을 다시 거친다. 다른 점만 적는다.

- 답은 두 군데서 온다: 채팅의 "S1. a", 문서의 결정 제목 `->` 옆. 둘 다 읽는다
- `->` 옆 답이 "추천안" 이면 추천안을 `@확정` 으로 옮긴다
- `->` 옆이 비어 있는 볼드 결정은 「열린 결정」에 그대로 두고 끝맺음 첫 줄에서 다시 묻는다
- 이탤릭 결정에 다른 옵션이 적히면, 그 결정의 「걸린 곳」을 모두 고치고 「정해진 결정」으로 옮긴다
- 요구사항 문서가 바뀌면(답 반영, 요구사항 추가) 「요구사항 추적」에서 바뀐 번호를 찾아 걸린 설계만 고친다. `@가정 ({ID} 추천안)` 자리는 답에 맞게 고치고 차이 목록을 지운다

## 끝맺음

- 첫 줄
    - `references/design.md` 「완성」이면: "완성 — 다음 단계로 넘어갈 수 있습니다." 와 다음 명령 한 줄 (예: `/sdd:task ~/.sdd/dotfiles/20261102143005_제휴카페-임직원-할인/`)
    - 아니면: 다음에 답할 결정 하나. 요구사항 문서의 열린 결정이 먼저다. 구체 예시와 추천안을 붙인다
- 둘째 줄: 문서 경로(클릭 가능한 `path`)
- 무엇을 썼는지·바꿨는지 불릿 5개 이하. 「요구사항 추적」 숫자(예: 18/18)를 포함한다. 문서 내용을 다시 늘어놓지 않는다
- 역반영 제안이 있으면 요구사항 문서에 올릴 결정 문장을 한 줄씩, 3개 이하
- 구현 전에 확인할 위험은 3개 이하, 한 줄씩

## 하지 않는 것

- 코드를 바꾸지 않는다
- 요구사항 문서를 고치지 않는다. 역반영은 제안만 하고, 반영은 `sdd:draft` 의 「답 반영」이 한다
- 요구사항 문서의 규칙·수치를 설계 문서에 옮겨 적지 않는다
- 요구사항 문서의 열린 결정을 이유로 멈추지 않는다
- 인수 조건을 Gherkin 이나 테스트 문장으로 다시 쓰지 않는다
