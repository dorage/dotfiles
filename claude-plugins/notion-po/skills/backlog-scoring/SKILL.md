# 백로그 스코어링

Circularlabs 백로그 항목의 **평가 속성**을 채우는 skill 이에요. 각 항목을 읽고 아래 기준(rubric)에 따라 점수를 매긴 뒤 Notion 에 반영해요.

- 대상 백로그 DB / data source ID · 전체 속성 맵은 [po 스킬](../po/SKILL.md) 의 "백로그 DB 속성" 을 단일 출처로 써요.
- `ntn` CLI 사용법 · 인증 · **비대화 호출 주의(`< /dev/null`, 한글 바디는 `-d @file`, `timeout`)** 는 [notion 스킬](../notion/SKILL.md) 을 따라요.
- 백로그 data source ID: `a07f68d9-4082-8359-9579-07c5578db49e`
- 점수 축(작업크기=스토리포인트, 가치·긴급도·위험도, WSJF)의 개념·근거는 [스크럼 실전 플레이북](../../references/scrum-playbook.md) 6~7장을 참고해요. 이 스킬의 rubric 은 그 원칙을 우리 백로그 실데이터로 구체화한 거예요. (플레이북 척도의 `13/20` 은 쓰지 않고 `1/2/3/5/8` 로만 매겨요.)

## 대상 속성

| 속성 | 타입 | 값 | 채우는 것 |
| :-- | :-- | :-- | :-- |
| `작업크기` | select | `1`·`2`·`3`·`5`·`8` | 개발/구현 규모(공수) |
| `비즈니스가치` | select | `1`·`2`·`3`·`5`·`8` | 비즈니스 임팩트 |
| `긴급도` | select | `1`·`2`·`3`·`5`·`8` | 시급성 |
| `위험도` | select | `1`·`2`·`3`·`5`·`8` | 불확실성/리스크 |
| `가치판단` | rich_text | 자유 서술 | 위 점수의 근거·판단 요약 |

> `작업크기`·`비즈니스가치`·`긴급도`·`위험도` 는 `우선순위`·`스토리포인트`(formula)의 입력이에요. 값은 반드시 `1/2/3/5/8` 중 하나(피보나치)여야 해요. 그 사이 값(4,6,7)은 쓰지 않아요.

### 점수 모델 (formula 근거)

Notion formula 실측 기준으로 이렇게 계산돼요:

- **`스토리포인트` = `작업크기`** (그대로)
- **`우선순위` = (`위험도` + `긴급도` + `비즈니스가치`) ÷ `작업크기`** — WSJF(가치÷규모) 구조

즉 `작업크기` 는 스토리포인트이자 우선순위의 **분모**예요. 공수를 정확히 매겨야 우선순위가 왜곡되지 않아요.

## 평가 기준 (rubric)

> 네 개 select(`작업크기`·`비즈니스가치`·`긴급도`·`위험도`)와 `가치판단` 형식은 지난주 스프린트(‘선결제·탄소포인트…’) 백로그의 실제 점수·가치판단 메모로 보정·검증했어요. 스코어링할 때 이 기준을 그대로 적용하고 임의 해석을 하지 않아요. `2`·`5` 점대는 관측이 적어 보간했으니, 새 스프린트 데이터가 쌓이면 재보정해요.

### 작업크기 (공수) — 분해 후 합산

작업을 **구성요소로 분해 → 각 요소 점수 합산 → `{1,2,3,5,8}` 로 반올림**해요. (팀이 `가치판단` 메모에 이미 이렇게 적고 있어요.)

**1) 구성요소 기준점** (요소 1건당)

| 구성요소 | 점수 | 실증(지난주 스프린트) |
| :-- | :-: | :-- |
| 기존 백엔드/앱 로직 수정 | 1 | PG/VAN "백엔드 코드 수정=1" |
| 신규 도메인/백엔드 로직 개발 | 2 | 선결제 도메인로직, EasyPay 도메인 로직 신규 |
| 신규 API 개발 | 1 | 선결제 "API 신규개발" |
| 어드민/기존 프론트 수정 | 1 | 공급사 권한 "어드민 프론트 수정" |
| 프론트 컴포넌트 추가 | 2 | PG/VAN "프론트 컴포넌트 추가=2" |
| 프론트 리팩토링 | 1 | 매출현황 "프론트 리팩토링=1" |
| 신규 프론트 플로우 개발 | 2 | NICE "신규 회원가입 플로우" |
| 외부 시스템 연동(웹뷰/외부 통신) | 2 | NICE "외부요소 통신(웹뷰)" |
| DB 마이그레이션(컬럼 추가) | 1 | 소프트딜리트 "추가 컬럼 마이그레이션" |
| DB 마이그레이션(구조 변경/대규모) | 2 | |
| 인프라 작업(배포/CI/리소스) | 2 | 탄중포 "인프라 작업 동반" |
| 테스트 작성/업데이트 | 1 | 선결제 "테스트 업데이트" |
| 다중 클라이언트(웹+앱) | 각 프론트를 개별 계산 | 선결제 카페 "웹프론트+앱프론트" |

**2) 가산 수정자**

- 정산·도메인 광범위 파급, 기존 고객사 재작업 요구: **+2~3** (선결제 카페=8, EasyPay=8)
- 조사가 필요한 미확정 범위: **+1** (불확실하면 위험도로도 반영)

**3) 반올림** — 합계를 가장 가까운 `{1,2,3,5,8}` 로, **동점이면 올림**:

| 합계 | → 작업크기 |
| :-: | :-: |
| ≤1 | 1 |
| 2 | 2 |
| 3 | 3 |
| 4 | 5 |
| 5·6 | 5 |
| 7 이상 | 8 |

> ⚠️ 실제 옵션은 `1/2/3/5/8` — **3은 존재하고 4는 없어요**. (합계 3은 3 그대로, 4가 5로 올라감.)

**4) 상한·분할** — 합계가 8을 넘으면 백로그가 과대예요. 8로 캡하되 **작업 분할을 권고**해요. (지난주 '선결제 카페'는 8이었고 취소됨.)

**5) 스파이크/조사 항목** — 순수 조사·[스파이크] 항목은 **`작업크기`(및 나머지 점수)를 공란으로 둬요**(팀 관행 확정). 공란이면 `우선순위`·`스토리포인트` formula 에서 자연히 제외돼요. 억지로 점수를 매기지 않아요.

**계산 예시**
- PG/VAN 매출확인: 백엔드 수정(1) + 프론트 컴포넌트(2) = 3 → **3**
- 선결제 도메인로직: 도메인로직(2)+API 신규(1)+테스트(1)+DB마이그(1) = 5 → **5**
- EasyPay 변경범위: DB마이그(1)+도메인 로직 신규(2)+클라 결제 로직(2)+기존 고객사 재작업(+2) = 7 → **8**

> 세 속성 모두 `우선순위` 의 **분자**라 점수가 클수록 우선순위가 올라가요. 특히 `위험도` 는 이 모델에서 **"리스크·영향도(클수록 먼저 다뤄야 함)"** 로 써요(팀 확정). `2`·`5` 는 지난주 관측이 적어 `1`↔`3`, `3`↔`8` 사이를 보간한 값이에요.

### 가치판단 (서술)

각 점수의 근거를 팀 표준 형식으로 적어요. 지난주 스프린트에서 실제로 쓰던 형식:

```
작업크기 - <구성요소 나열: 예) DB마이그레이션, API 신규개발, 프론트 컴포넌트 추가>
비즈니스 - <비즈니스가치 점수의 근거 한 줄>
긴급도 - <긴급도 점수의 근거 한 줄>
위험도 - <위험도 점수의 근거 한 줄>
```

- 각 줄은 해당 점수를 **왜 그렇게 줬는지** 사실 근거로 채워요(정량 지표·기한·고객사명 있으면 인용).
- 근거가 부족한 항목은 추측하지 말고 "근거 부족"으로 남기고 사용자에게 물어요.

## 절차

### 1. 대상 확정

- 단건: 백로그 페이지 ID(또는 URL) 를 받음.
- 다건: 특정 스프린트/상태의 미평가 항목 일괄. 예로 `상태 = 제품` 이면서 점수가 빈 항목:

  ```bash
  ntn datasources query a07f68d9-4082-8359-9579-07c5578db49e --json < /dev/null \
    | python3 -c "
  import sys,json
  for p in json.load(sys.stdin).get('results',[]):
      pr=p['properties']
      name=''.join(x['plain_text'] for x in pr.get('작업 이름',{}).get('title',[]))
      def sel(k): return (pr.get(k,{}).get('select') or {}).get('name')
      missing=[k for k in ('작업크기','비즈니스가치','긴급도','위험도') if not sel(k)]
      if missing: print(p['id'],'|',name,'| 빈 항목:',missing)
  "
  ```

### 2. 항목 읽기 (근거 수집)

각 항목의 `작업 이름`·`메모`·`에픽`(테마)·`기간` 등을 읽어 판단 근거를 만들어요. 정보가 부족하면 추측하지 말고 "근거 부족"으로 표시하고 사용자에게 물어요.

```bash
ntn pages get <BACKLOG_PAGE_ID>            # 본문/메모 확인
# 속성값만 볼 땐 datasources query 결과의 properties 사용
```

### 3. 점수 산정

위 [평가 기준](#평가-기준-rubric--️-사용자-작성-영역) 을 적용해 4개 select 점수(`1/2/3/5/8`)와 `가치판단` 서술을 만들어요.

- 기준에 근거해 매기고, `가치판단` 에 각 점수의 근거를 요약해요.
- 애매하면 낮은 쪽/보수적으로 잡고 `가치판단` 에 불확실성을 명시해요.
- **기준(rubric)이 비어 있으면 스코어링하지 말고** 사용자에게 기준부터 요청해요.

### 4. 반영 (write)

대화형이면 산정 결과를 표로 먼저 보여주고 승인받은 뒤 PATCH 해요. 다건이면 항목별로 진행 상황을 로그로 남겨요.

```bash
cat > /tmp/backlog_score.json <<JSON
{
  "properties": {
    "작업크기":     {"select": {"name": "5"}},
    "비즈니스가치": {"select": {"name": "8"}},
    "긴급도":       {"select": {"name": "3"}},
    "위험도":       {"select": {"name": "2"}},
    "가치판단":     {"rich_text": [{"text": {"content": "<근거 서술>"}}]}
  }
}
JSON
timeout 60 ntn api /v1/pages/<BACKLOG_PAGE_ID> -X PATCH -d @/tmp/backlog_score.json < /dev/null
```

- 응답 `object` 가 `error` 면 중단하고 `code`/`message` 를 보고해요.
- 이미 값이 있는 항목을 덮어쓸 땐 기존 값을 로그로 남겨요(되돌림 대비).

### 5. 보고

항목별 `작업크기/비즈니스가치/긴급도/위험도` 와 `가치판단` 한 줄, 반영된 URL 을 표로 정리해 보고해요.

## 주의

- select 값은 반드시 `1/2/3/5/8`. 그 외 값은 Notion 이 새 옵션을 만들어 버리므로 절대 쓰지 않아요.
- `우선순위`·`스토리포인트`(formula)는 직접 못 써요 — 위 입력 4개만 바꾸면 자동 계산돼요.
- 점수는 rubric 근거로만. rubric 밖 임의 기준으로 매기지 않아요.
